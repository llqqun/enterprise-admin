## 1. 通用约定

### 1.1 统一响应信封

每个响应（包括错误）都是：

```json
{ "code": <int>, "msg": "<string>", "data": <any|null> }
```

- 成功：`app/core/response.py::success(data, msg="操作成功")` → `code = 200`。
- 列表（P0 无消费方）：`app/core/response.py::page(rows, total)` → `data = {"rows": [...], "total": n}`，
  `msg = "查询成功"`。
- 错误：见 §1.4。

**HTTP 状态码是语义化的**，不做"全部返回 200 再在业务码里判错"。绝大多数情况下
`code == HTTP status`。

### 1.2 分页契约

| 入参 | 默认 | 边界行为 |
|---|---|---|
| `page_num` | 1 | `< 1` 被钳制为 1 |
| `page_size` | 10 | `< 1` 钳制为 1；`> 100`（`MAX_PAGE_SIZE`）钳制为 100 |

出参 `{"rows": [], "total": 0}`。

> **P0 现状**：`PageParams` 与 `page()` 只有 `tests/test_response_and_errors.py` 在引用，
> **没有任何路由消费它们**。所以下表里没有一条接口带分页参数 —— 第一个列表接口属于 P1。

### 1.3 认证方式

- 方案：`OAuth2PasswordBearer`，`tokenUrl = {API_V1_PREFIX}/auth/login`，**`auto_error=False`**
  （`app/core/deps.py:30-33`）。`auto_error=False` 是刻意的：缺失 `Authorization` 头时得到的是本
  项目的 `{code,msg,data}` 信封，而不是 FastAPI 内建的 `{"detail": "Not authenticated"}`。
- 请求头：`Authorization: Bearer <access_token>`。
- 校验顺序（`app/core/deps.py::get_current_user`，:62-111）：

  1. 无令牌 → `401 "未提供身份凭证"`（`MISSING_CREDENTIALS_MSG`）；
  2. `decode_token(token, "access")` 失败（签名/过期/格式/type 不符）→ `401 "登录状态已失效，请重新登录"`
     （`SESSION_REJECTED_MSG`）；
  3. 按 `access_jti` + `revoked=0` 查 `sys_user_token`；查不到或 `access_expire < utcnow()` →
     同一个 401 消息；
  4. 查 `sys_user`；用户不存在或 `status != '0'` → 同一个 401 消息；
  5. 装配 `CurrentUser`：`is_admin = "admin" in 启用角色的 role_key`；
     `perms = {"*:*:*"}`（超管）或该用户所有**启用角色**的**启用菜单**的 `perms` 集合。

  **三种失败共用同一条消息**是刻意的（`deps.py:67-72` 的 docstring）：区分"无此会话"/"已过期"/
  "已撤销"等于白送一个探测预言机。

### 1.4 错误码总表

| HTTP | `code` | `msg` | `data` | 触发来源 |
|---|---|---|---|---|
| 400 | 400 | 业务消息（见各接口） | `null` | `BusinessException`，由 `_handle_app_exception` 渲染 |
| 401 | 401 | `"未提供身份凭证"` 或 `"登录状态已失效，请重新登录"` | `null` | `UnauthorizedException` |
| 403 | 403 | `"没有操作权限"`（默认） | `null` | `ForbiddenException`（`require_perm` 拒绝） |
| 404 | 404 | `"Not Found"` **（英文，框架串）** | `null` | `StarletteHTTPException`，路径不存在 |
| 405 | 405 | `"Method Not Allowed"` **（英文，框架串）** | `null` | `StarletteHTTPException`，方法不匹配 |
| 422 | 422 | `"参数校验失败"` | **字段数组** `[{"field","msg"}]` | `RequestValidationError` 或 `ValidationException` |
| 500 | 500 | `"系统内部错误，请稍后重试"` | `null` | 未捕获异常（含数据库不可用） |

两个必须记住的细节：

1. **`404`/`405` 的 `msg` 是英文框架串**，不是中文。只有应用主动抛的 `AppException` 才有中文 `msg`。
2. **`422` 的 `data` 是数组而不是 `null`**：`{"field": "password", "msg": "Field required"}`。
   `field` 是剥掉 `body`/`query`/`path`/`header`/`cookie` 前缀后的点分路径。**整个 JSON 体解析失败**时，
   `field` 会是字符偏移量（如 `"1"`），那是错误位置而非字段名。

实测样本（真实进程 + `curl`）：

```jsonc
// GET /api/v1/auth/profile  无令牌
{"code":401,"msg":"未提供身份凭证","data":null}

// POST /api/v1/auth/login  {"username":"admin"}
{"code":422,"msg":"参数校验失败","data":[{"field":"password","msg":"Field required"}]}

// POST /api/v1/auth/login  80 字符密码
{"code":422,"msg":"参数校验失败","data":[{"field":"password","msg":"Value error, 密码不能超过 72 字节"}]}

// GET /api/v1/nope
{"code":404,"msg":"Not Found","data":null}

// GET /api/v1/auth/login  （方法不对）
{"code":405,"msg":"Method Not Allowed","data":null}
```

### 2.2 `GET /api/v1/auth/captchaImage`

| 项 | 值 |
|---|---|
| 位置 | `app/api/v1/auth.py:18-20` → `auth_service.build_captcha()`（`services/auth_service.py:74`） |
| 所需权限 | 无（未认证可达） |
| 请求参数 | 无 |
| 成功响应 | `200 {"code":200,"msg":"操作成功","data":{"uuid":"<32位hex>","img":"<base64 PNG，不带 data: 前缀>","captcha_enabled":true}}` |
| 可能错误 | `422`（无参数）、`405`、`500`（**不查数据库**，所以 500 的概率极低） |

行为细节：

- 答案存进进程内缓存，key `captcha:{uuid}`，TTL **120 秒**（`CAPTCHA_TTL_SECONDS`，`auth_service.py:40`）。
- 字符集 `23456789ABCDEFGHJKLMNPQRSTUVWXYZ`，长度 4，排除了 `0/O`、`1/I/l`（`core/security.py:30-33`）。
- 图片 120×40 PNG，6 条干扰线 + 120 个噪点（`generate_captcha`，`security.py:125-173`）。
- **`CAPTCHA_ENABLED=false` 时**仍然返回一个 `uuid`（保证客户端请求形态不变），但 `img` 为空串、
  `captcha_enabled` 为 `false`。实测响应：
  `{"code":200,"msg":"操作成功","data":{"uuid":"eeb8...","img":"","captcha_enabled":false}}`
- `.env` 里未显式设置 `CAPTCHA_ENABLED` 时，`Settings.CAPTCHA_ENABLED` 的默认值是 **`true`**
  （`core/config.py:38`）—— 即安全默认。

### 2.3 `POST /api/v1/auth/login`

| 项 | 值 |
|---|---|
| 位置 | `app/api/v1/auth.py:23-35` → `auth_service.authenticate(...)`（`services/auth_service.py:159`） |
| 所需权限 | 无（未认证可达） |
| 请求体 | `LoginRequest`（`schemas/auth.py:9`） |
| 成功响应 | `200 {"code":200,"msg":"登录成功","data":{"access_token":"<JWT>","refresh_token":"<JWT>","expires_in":1800,"token_type":"bearer"}}` |
| 可能错误 | `400` / `422` / `500`（见下） |

**请求体**（`schemas/auth.py::LoginRequest`）：

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| `username` | `str` | **是** | `min_length=1`, `max_length=30` | 账号 |
| `password` | `str` | **是** | `min_length=1`；UTF-8 编码后 `<= 72` 字节 | 密码。超 72 字节 → 422（bcrypt 上限） |
| `code` | `str` | 否 | 默认 `""`，`max_length=8` | 验证码 |
| `uuid` | `str` | 否 | 默认 `""`，`max_length=64` | 验证码会话标识 |

`code`/`uuid` **刻意不设 `min_length`**（`schemas/auth.py:12-16` 的注释）：是否必填取决于运行时配置
`CAPTCHA_ENABLED`，那是验证码服务的职责而非 schema 的。验证码启用时空 `code` 应得到服务层的
**400**（不是校验层的 422）—— 两者对客户端含义不同。

> **文档偏差**：P0 实施计划（`docs/superpowers/plans/2026-10-17-p0-foundation-and-login.md` 的
> Global Constraints）写的是"登录口令长度 6–32 字符"。**代码里没有 6–32 这个区间**，只有
> `min_length=1` 与 72 字节上限。以代码为准。

**服务层的判定顺序是刻意的**（`auth_service.py:166-171` 的 docstring）：**验证码 → 锁定 → 凭据**。
理由：验证码错误绝不能计入锁定，否则任何人只要知道用户名就能把该账号锁死。

| 分支 | 条件 | HTTP / 响应 |
|---|---|---|
| 验证码失效 | 缓存里没有该 `uuid`，或 `code` 不匹配（大小写不敏感） | `400 {"code":400,"msg":"验证码已失效，请刷新后重试","data":null}` |
| 账号已锁定 | `cache.get("login_fail:{归一化账号}") >= 5` | `400 {"code":400,"msg":"密码错误次数过多，账号已锁定 10 分钟","data":null}` |
| 用户不存在 **或** 密码错误 | —— | `400 {"code":400,"msg":"用户名或密码错误","data":null}`（**两种情况消息完全相同**） |
| 账号停用 | `user.status != '0'` | `400 {"code":400,"msg":"账号已停用，请联系管理员","data":null}` |
| 账号已逻辑删除 | `del_flag = '2'` | 与"密码错误"完全相同：`400 "用户名或密码错误"` |
| 密码超 72 字节 | schema 校验 | `422`，`data[0].msg = "Value error, 密码不能超过 72 字节"` |
| 缺 `username`/`password` | schema 校验 | `422`，`data[0] = {"field":"password","msg":"Field required"}` |
| 数据库不可用 | 驱动异常 | `500 {"code":500,"msg":"系统内部错误，请稍后重试","data":null}`（实测于 `docs/P0验收记录.md` 第 130 行） |

**成功路径的副作用**（全部在同一个事务里，由 `get_db` 在端点返回后 `commit()`）：

1. 插入一行 `sys_user_token`（`access_jti` / `access_expire` / `refresh_jti` / `refresh_expire` /
   `login_ip` / `browser` / `os` / `login_time` / `revoked=false`）；
2. 更新 `sys_user.login_ip` 与 `sys_user.login_date`；
3. 删除失败计数器 `login_fail:{...}`；
4. 插入一行 `sys_login_log`（`status='0'`，`msg="登录成功"`）。

**失败路径也会写审计**：每次凭据失败、锁定拒绝、停用拒绝都插入一行 `sys_login_log`
（`status='1'`，`msg` 为对应提示）。`record_login_log`（`services/log_service.py:11`）把每个列
按 schema 宽度截断（`user_name[:30]`、`ipaddr[:128]`、`browser[:64]`、`os[:64]`、`msg[:255]`），
理由是"超长 User-Agent 不能让写审计日志变成登录失败"。

**防时序侧信道**：用户不存在时用 `_dummy_password_hash()`（一个真实 bcrypt cost-12 哈希，
`lru_cache(maxsize=1)` 惰性计算）做一次等价的 `verify_password`，使响应耗时与真实账号一致
（`auth_service.py:63-71`、:189-190）。

**登录IP 的来源**：`client_ip(request)`（`utils/request_info.py:35`）优先取
`X-Forwarded-For` 的第一跳，其次 `X-Real-IP`，最后 `request.client.host`。
这个头是**客户端可伪造的**，因此只作为审计元数据，**绝不作为授权输入**（docstring 明确写了）。

**锁定计数键**：`"login_fail:" + username.strip().casefold()`（`auth_service.py:52-60`）。归一化是
必须的，因为 `utf8mb4_0900_ai_ci` 排序规则下 `ADMIN` 会命中 `admin` 那一行 —— 按原始输入串计数
等于给每种大小写拼写各发 5 次机会。`tests/test_lockout.py` 的 5 条用例守这件事。

### 2.4 `GET /api/v1/auth/profile`

| 项 | 值 |
|---|---|
| 位置 | `app/api/v1/auth.py:38-43` → `auth_service.build_profile(db, current)`（`services/auth_service.py:264`） |
| 所需权限 | **登录即可**（`Depends(get_current_user)`，不要求任何权限码） |
| 请求参数 | 无 |
| 成功响应 | `200 {"code":200,"msg":"操作成功","data":{"user":{...},"roles":[...],"permissions":[...]}}` |
| 可能错误 | `401`（无令牌 / 令牌失效 / 账号停用或已删除）、`405`、`500` |

**响应体**（`schemas/auth.py::ProfileResponse` / `UserProfile`）：

```jsonc
{
  "user": {
    "user_id": 1, "user_name": "admin", "nick_name": "超级管理员",
    "dept_id": 1, "email": null, "phonenumber": null,
    "sex": "2", "avatar": null, "status": "0"
  },
  "roles": ["admin"],
  "permissions": ["*:*:*"]
}
```

- `UserProfile` **没有 `password` 字段**（`schemas/auth.py:47-52` 的注释）：响应不可能泄漏它，
  因为字段本身不存在 —— 这比"记得剔除"更强。`tests/test_authz.py::test_profile_never_returns_password` 守着。
- `roles` 是**启用角色**的 `role_key` 列表（`status == '0'`，`auth_service.py:274`）。
- `permissions`：超管直接是 `["*:*:*"]`；非超管是 `sorted(current.perms)` —— 即 `get_current_user`
  已经算好的同一个集合（`auth_service.py:275`）。**这就是"前端隐藏的按钮与后端放行的调用按构造一致"
  的实现依据。**
- 实测（种子账号 `manager`）：`{"roles":["dept_manager"],"permissions":["monitor:online:list","system:user:list","system:user:query"]}`。
- 零角色 / 零权限账号**不是错误**：`permissions` 为 `[]`，HTTP 200
  （`tests/test_authz.py::test_profile_of_a_permissionless_user_is_not_an_error`）。

### 2.5 `GET /api/v1/auth/routers`

| 项 | 值 |
|---|---|
| 位置 | `app/api/v1/auth.py:54-59` → `menu_service.get_routers(db, current)`（`services/menu_service.py:75`） |
| 所需权限 | **登录即可**（`Depends(get_current_user)`） |
| 请求参数 | 无 |
| 成功响应 | `200 {"code":200,"msg":"操作成功","data":[ <路由节点>... ]}` |
| 可能错误 | `401`、`405`、`500` |

**节点结构**（`menu_service._to_route`，:23-32）：

```jsonc
{
  "name": "System",                    // route_name；为空时回退为 "Menu{menu_id}"
  "path": "/system",
  "hidden": false,                     // = (menu.visible != "0")
  "component": null,                   // 目录节点为 null
  "meta": { "title": "系统管理", "icon": "Setting" },
  "children": [
    {
      "name": "SystemUser", "path": "user", "hidden": false,
      "component": "system/user/index",
      "meta": { "title": "用户管理", "icon": "User" },
      "children": []
    }
  ]
}
```

**选中规则**（`menu_service._visible_menus`，:35-63）：

| 条件 | 是否生效 |
|---|---|
| `menu_type IN ('M','C')`（排除 `F` 按钮） | ✅ |
| `status = '0'`（排除停用菜单） | ✅ |
| 非超管：`JOIN sys_role_menu` + `JOIN sys_user_role` + `JOIN sys_role`，且 `sys_role.status = '0'` | ✅ |
| `sys_role.del_flag = '0'` | ✅（全局逻辑删除过滤器自动附加） |
| `sys_menu.visible = '0'` | ❌ **不过滤**，只翻译成载荷里的 `hidden` |

排序为 `ORDER BY parent_id, order_num`；因为角色 join 可能重复匹配同一菜单，取了 `.unique()`。

**零菜单是成功而不是错误**（`menu_service.py:79-80` 的 docstring）：实测 `staff` 账号得到
`200 {"code":200,"msg":"操作成功","data":[]}`，前端据此显示空侧边栏而不是白屏
（`tests/test_menu.py::test_routers_for_a_role_without_menus_is_an_empty_list`）。

**已停用 / 已逻辑删除的角色不下发菜单**（`tests/test_menu.py` 的三条回归用例）。这是独立评审
发现并修复的 Important 缺陷：接口层（`require_perm`）与 profile 层都忽略停用角色，唯独菜单层
当时没 join `sys_role`，导致同一账号在不同层得到互相矛盾的答案。

### 2.6 `POST /api/v1/auth/refresh`

| 项 | 值 |
|---|---|
| 位置 | `app/api/v1/auth.py:46-51` → `auth_service.refresh_tokens(db, payload.refresh_token)`（`services/auth_service.py:233`） |
| 所需权限 | 无（未认证可达；凭证是请求体里的 refresh token） |
| 请求体 | `RefreshRequest`：`{"refresh_token": "<JWT>"}`（`min_length=1`） |
| 成功响应 | `200 {"code":200,"msg":"操作成功","data":{"access_token":"...","refresh_token":"...","expires_in":1800,"token_type":"bearer"}}` |
| 可能错误 | `401`（refresh 无效/过期/已撤销，或账号停用/已删除）、`422`（`refresh_token` 缺失或空串）、`405`、`500` |

**轮换语义**（`auth_service.py:233-261`）：

1. `decode_token(refresh_token, "refresh")` —— 用 access 令牌充当 refresh 会在此被拒（`type` 校验）；
2. 按 `refresh_jti` + `revoked=0` 查 `sys_user_token`；查不到或 `refresh_expire < utcnow()` → 401；
3. 查用户，不存在或 `status != '0'` → 401；
4. `record.revoked = True`；
5. **用同一个事务**签发新的令牌对，新行沿用旧行的 `login_ip` / `browser` / `os`。

实测确认的连带效果：**刷新之后旧 access 令牌立即失效**（因为撤销的是整行，不是单个 jti）。
实测序列：

| 步骤 | 结果 |
|---|---|
| 登录得到 `A1`/`R1`，`A1` 访问 profile | 200 |
| 用 `R1` 刷新得到 `A2`/`R2` | 200 |
| 用 `A1` 访问 profile | **401** |
| 用 `A2` 访问 profile | 200 |
| 用 `R1` 再刷新（重放旧 refresh） | **401** |

**为什么必须轮换**（`auth_service.py:236-239`）：轮换让重放可检测 —— 旧记录在同一事务里被撤销，
所以被盗的 refresh 令牌最多只能用一次，而且合法客户端的下一次刷新会失败，这是一个可见信号。

> **P0 已知未修**：轮换**没有宽限期**，所以两个标签页同时刷新时，读到同一个旧 refresh 令牌的
> 后者会被强制登出。列在 `docs/P0决策记录.md` 第四节第 9 条。前端一侧用**单飞刷新**在同一页面内
> 规避了并发（`frontend/src/utils/request.ts` 的 `refreshPromise`），但跨标签页不共享这个 Promise。

### 2.7 `POST /api/v1/auth/logout`

| 项 | 值 |
|---|---|
| 位置 | `app/api/v1/auth.py:62-68` → `auth_service.revoke_by_access_jti(db, current.access_jti)`（`services/auth_service.py:284`） |
| 所需权限 | 登录即可（`Depends(get_current_user)`） |
| 请求体 | 无（`content-type` 任意；前端发的是空 POST） |
| 成功响应 | `200 {"code":200,"msg":"退出成功","data":null}` |
| 可能错误 | `401`（未登录或令牌已失效）、`405`、`500` |

行为：按 `current.access_jti` 找到 `sys_user_token` 那一行，置 `revoked = True`。**撤销的是整行**，
因此配对的 refresh 令牌一起失效（docstring：`revoking the whole row ... is what makes logout mean
"this session is over"`）。找不到行时**静默返回**（`auth_service.py:293-294`）—— 登出是幂等的。

`CurrentUser.access_jti` 字段（`deps.py:45-47`）存在的唯一目的就是让这条接口结束**当前这一个**
会话，而不是该账号的所有会话。它来自 `get_current_user` 里已经验签过的那个 `jti`，所以登出路由
不需要再解一次令牌。

实测：登出后原 access 令牌访问 profile → 401；配对的 refresh 令牌刷新 → 401。

### 2.8 仅 `DEBUG=true` 时存在的路由（**不在 OpenAPI 里**）
