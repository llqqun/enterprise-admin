# P0 决策记录

本文件是 P0 实施过程中**所有偏离原计划的决定**与**已知但未修复的问题**的完整清单。

它由实施 ledger（`.superpowers/sdd/...`，属于临时工作目录、交付后删除）固化而来。之所以单独留存：
原计划写于动手之前，而真正的工程判断发生在动手之后 —— 哪些坑必须绕、哪些取舍值得付代价，
只有做过才知道。这些决定不该随临时目录一起消失。

每条裁定的格式为：**决定 → 为什么 → 判断错误时的代价**。

- Pre-flight: Ruling: the `admin_current_user` and `no_menu_current_user` fixtures are added to `tests/conftest.py` in Task 10, built by inserting the dept/role/user/menu rows they need. 鈥?Why: Task 10 is the first task that consumes `CurrentUser`. Cost if wrong: fixtures get built one task later than ideal.
- Task 1: Ruling: MySQL error/slow logs live at `D:\devtools\mysql-logs` instead of the spec Appendix B path `D:\devtools\mysql-data\logs` 鈥?a `logs\` subfolder inside datadir makes `mysqld --initialize-insecure` abort with MY-010457 ("the data directory has files in it"), so the two must be separate trees. Cost if wrong: one path to correct in the docs; MySQL keeps working either way.
- Task 2: Ruling: `requirements.txt` also lists `cryptography`, which the plan's dependency block omitted. MySQL 8 defaults to the `caching_sha2_password` auth plugin, and a driver cannot complete that handshake over a non-TLS loopback connection without it. Cost if wrong: one unused transitive dependency (small, and a prebuilt wheel).
- Task 2: Ruling: dropped the plan's `anyio_backend` fixture from `tests/conftest.py`. `pytest.ini` drives async tests through pytest-asyncio's `asyncio_mode = auto` (confirmed in the run header: `asyncio: mode=Mode.AUTO`), so an anyio marker fixture would be dead code. Cost if wrong: add it back if anyio-marked tests ever appear.
- Task 2: Ruling: `SECRET_KEY` has no default, and `.env` is generated with a random 64-hex value. A committed placeholder is a real credential smell in a portfolio project, and a missing key should fail loudly at startup rather than silently sign tokens with a known constant. Cost if wrong: a fresh clone must create `.env` before the app will boot (Task 16's `init.ps1` does it).
- Task 3: Ruling: `RequestIdMiddleware` is written as plain ASGI middleware instead of subclassing Starlette's `BaseHTTPMiddleware`. Starlette resolved to 1.8.0 (a major version bump) and this middleware only needs to touch the scope and the response headers, so depending on a base class whose signature may have changed buys nothing and costs a task group per request. Cost if wrong: none observed 鈥?the `X-Request-Id` assertion passes.
- Task 3: Ruling: the test client is built with `ASGITransport(app=app, raise_app_exceptions=False)`. Starlette's `ServerErrorMiddleware` renders the 500 response and *then* re-raises so the server can log it; a real HTTP client therefore sees the response. Without this flag the "unhandled exception hides internals" test could never observe the handler's output 鈥?it would see the raised `RuntimeError` instead. Cost if wrong: a genuinely raised exception inside a test surfaces as a 500 response rather than a traceback, so the failing assertion (not the exception) is what reports it.
- Task 4: Ruling: supersedes the setup pre-flight ruling about *where* `install_soft_delete_filter` gets called. The spec (搂5.1) requires **global** filtering ("`with_loader_criteria` 鍏ㄥ眬杩囨护锛屼笟鍔′唬鐮佹棤闇€鎵嬪啓 `WHERE del_flag='0'`"), and a filter that works only when each call site remembers to install it is exactly the leak the spec wants closed. Implemented as a `do_orm_execute` listener registered once at import, so it is active for every session including ones no task anticipated. `install_soft_delete_filter(session)` is kept with honest semantics: an idempotent belt that guarantees the listener is attached. Cost if wrong: a session that deliberately wants unfiltered reads must opt out through `include_deleted()`; that escape hatch exists for exactly this.
- Task 5: Ruling: added `backend/app/models/associations.py`, which the plan's per-module file list does not mention. The four composite-key link tables carry no audit columns and no behaviour, so splitting them across the modules they connect would scatter one concept over four files. Cost if wrong: a reader looking for `sys_user_role` opens a file named by what it is rather than by which side it touches.
- Task 5: Ruling: added `RemarkMixin` to `app/db/base.py` (Task 4's file). Spec 搂5.1 lists `remark` as a common field on the business tables, but the plan's `TimestampMixin` carries only the four audit columns, and the append-only log/session tables must not grow a remark. A separate mixin keeps both statements true. Cost if wrong: one extra mixin in each class declaration.
- Task 5: Ruling: `sys_menu` deliberately has **no** `del_flag`. A removed menu must actually disappear, otherwise its `perms` code lingers in the permission set of every role that held it. Spec 搂5.1 marks `del_flag` as 鎸夐渶 (as needed), and menus are the case where it is not needed. Cost if wrong: deleting a menu is irreversible 鈥?which is what the seed/reset path wants anyway.
- Task 6: Ruling: every `decode_token` failure raises the identical message and the identical 401. This is the plan's Review Focus #1 鈥?telling a caller apart "expired" from "forged" hands them a probing oracle, and the frontend does not need the distinction because it keys off the status code plus the presence of a refresh token. Cost if wrong: a client that wanted to say "your session expired" cannot phrase it specifically.
- Task 6: Ruling: `hash_password` raises `ValueError` above bcrypt's 72-byte limit instead of truncating silently. Silent truncation means two different long passwords can authenticate the same account. The API schema must enforce the same byte limit so this is unreachable over HTTP (Task 8 owns that validator). Cost if wrong: a caller that ignores the contract gets a 500 rather than a 422.
- Task 7: Ruling: `MemoryCache` uses lazy expiry plus opportunistic pruning, and creates **no background sweeper task**. The plan's interface list mentions no sweeper; a sweeper would also outlive the event loop of any test that constructs a cache per test, producing "Task was destroyed but it is pending" noise and cross-test interference. Cost if wrong: a key that is written and never read again occupies memory until the next `set()` triggers pruning; with captcha/counter key populations that is negligible.
- Task 8: Ruling: added an autouse `_isolated_cache` fixture that clears the process-wide cache before and after every test. Found by a real failure: because `cache` is a module-level singleton (by design), `test_login_locks_after_five_failures` left `login_fail:admin = 5` behind, and every later test touching that account was silently locked out 鈥?7 tests failed for a reason that had nothing to do with the code they were testing. Cost if wrong: none; the fixture only removes cross-test state.
- Task 8: Ruling: set MySQL `default-time-zone='+00:00'` in `my.ini` (template **and** the live instance) so server-side `now()` agrees with the naive-UTC datetimes the application writes into `DATETIME` columns. Without it, `create_time` (server default) and `access_expire` (application value) would be in different zones on the same row, which is the kind of bug that surfaces months later as "expired tokens are still valid". Cost if wrong: log timestamps in the database read as UTC rather than local time.
- Task 8: Ruling: the login sequence is captcha 鈫?lockout 鈫?credentials, in that order. A wrong captcha must not increment the failure counter, otherwise anyone who knows a username can lock that account out without ever guessing its password. Cost if wrong: a locked account still requires a valid captcha to attempt a login, which is a small extra step for a legitimate user.
- Task 9: Ruling: authorization tests live in a new `tests/test_authz.py` instead of being appended to `test_auth.py` (which the plan named). Authentication ("who you are") and authorization ("what you may do") are different concerns; `test_auth.py` was already 330 lines, and mixing them means reading one to change the other. Cost if wrong: two files to search instead of one.
- Task 9: Ruling: `CurrentUser` carries one field the plan's interface list omits 鈥?`access_jti`. Logout must end *exactly* the session that presented the token, and that requires the `jti` from the token that was actually validated. Re-decoding the header inside the logout route would duplicate the validation logic. Cost if wrong: one extra field on a dataclass.
- Task 9: Ruling: `WILDCARD_PERM` and `ADMIN_ROLE_KEY` moved into `app/core/constants.py`, and `SESSION_REJECTED_MSG` into `app/core/security.py`. `app.core.deps` imports `app.services.auth_service`, so having the service import those names back from `deps` would have been a genuine import cycle, and `core/` importing `services/` is the wrong direction regardless. Cost if wrong: nothing; both are policy constants that belong with the other policy constants.
- Task 9: Ruling: added `app/utils/timeutil.py` with a single `utcnow()`. Two modules now need "current UTC as a naive datetime that matches the column type", and a second hand-written `datetime.now(timezone.utc).replace(tzinfo=None)` is how the two drift apart. Cost if wrong: one tiny module.
- Task 9: Ruling: Task 9 does **not** add the "routers placeholder" the plan mentions. A route that returns a stand-in shape would be a lie in the API surface for as long as it exists; `/auth/routers` is implemented whole in Task 10. Cost if wrong: Task 10 is slightly larger.
- Task 10: Ruling: added a `CAPTCHA_ENABLED` setting (default `true`), which no task in the plan mentions. Found by attempting the plan's own Step 6: because the captcha answer lives in the *server process's* in-memory cache, a separate HTTP client can never read it 鈥?so no automated check could drive a real login over real HTTP, and the whole "does it work outside the test harness" question stayed unanswerable. A toggle is also a standard capability (the frontend already carries a `captcha_enabled` field, and the equivalent exists in RuoYi as `sys.account.captchaEnabled`). Cost if wrong: it is a switch that weakens login if someone sets it false on an internet-facing deployment; `.env.example` says so and the default is safe.
- Task 10: Ruling: `build_tree` takes plain mappings, not ORM instances. All three callers (departments, menus, and whatever comes next) need a serialised node anyway, and accepting mappings keeps the helper free of ORM knowledge 鈥?it is a pure function and its tests need no database.
- Task 11: Ruling: `pinia-plugin-persistedstate` is **not** installed, although the plan's install command lists it. The plan's own Task 12 interface decides where the token lives (`utils/auth.ts` with explicit `getToken`/`setToken` on `localStorage`), so a second, implicit persistence mechanism for the same data would be a bug factory rather than a convenience.
