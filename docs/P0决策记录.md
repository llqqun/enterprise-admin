# P0 决策记录

本文件记录 P0 实施过程中**偏离原计划的决定**、**已知但本轮未修的问题**，以及**独立评审的结论**。

原计划写于动手之前，而真正的工程判断发生在动手之后 —— 哪些坑必须绕、哪些取舍值得付代价，只有做过
才知道。这些决定不该随实施 ledger（临时工作目录，已按流程删除）一起消失。逐任务的操作痕迹仍完整保留
在 20 个提交信息与 `docs/P0验收记录.md` 中；本文是决策层面的汇总。

每条裁定的格式：**决定 → 为什么 → 判断错误时的代价**。

## 一、环境与工程约定

| 决定 | 为什么 | 代价 |
|---|---|---|
| 用特性分支 `feat/p0-foundation` 而非 git worktree 隔离 | 计划里所有路径（项目根、MySQL 数据目录、venv、uploads、logs）都硬编码为 `D:\work\enterprise-admin` 系列，换 worktree 根目录会同时破坏计划与脚本 | 需要一次合并回 main |
| 三个脚本命名 `init.ps1` / `start.ps1` / `stop.ps1`（不是计划里的 `初始化.ps1` 等），并同步修正设计文档 §4/§12 | 本机 PowerShell 5.1 控制台代码页是 GB2312，UTF-8 无 BOM 的中文脚本内容会被误码解析；中文文件名经 cmd 逐层传参也易丢失 | 中文读者看到的文件名与原始设计不一致 |
| 所有 `.ps1` 内容纯 ASCII，中文说明只放 README 与 docs | 同上。此约定在整个 P0 中确实拦住了多次编码问题 | 脚本对中文读者不够友好 |
| 调用原生 exe 时放宽 `$ErrorActionPreference`（放弃计划要求的 `Stop`） | `Stop` 下原生程序往 stderr 写的正常输出（如 git)会变成终止性错误并中断脚本 —— 实测 `git checkout -b` 在成功后被中断 | 非预期的 cmdlet 失败不会中断脚本（见遗留项 8） |
| MySQL 错误日志放 `D:\devtools\mysql-logs`，而不是设计文档写的 `mysql-data\logs` | datadir 内任何文件都会让 `mysqld --initialize-insecure` 以 MY-010457 中止；且 MySQL 官方建议 datadir 只放数据 | 文档里一处路径需要修正 |
| 用 venv 级 `pip.ini` 把 pip 缓存指向 D 盘，由 `init.ps1` 自动创建 | 这是唯一既能随项目环境生效、又能持久化的位置；否则 `pip install` 会写 C 盘用户目录 | 一个容易被误认为含密钥的小文件 |
| npm registry 与 cache 写在项目级 `frontend/.npmrc`，不用 `npm config set --location=user` | 用户的全局 npm 配置属于用户，不属于这个项目 | 同上 |
| MySQL 设 `default-time-zone='+00:00'`（模板与运行实例都改） | 应用写的是 naive UTC，若服务端 `now()` 是本地时区，同一行里 `create_time` 与 `access_expire` 会处于不同时区 —— 这类 bug 几个月后会以「过期令牌仍然有效」的形式浮现 | 数据库里的日志时间显示为 UTC 而非本地时间 |
| 不装 `pinia-plugin-persistedstate`（计划里列了） | 计划自己的接口（`utils/auth.ts` 的显式 get/set）已经决定了令牌存放位置，再叠一套隐式持久化同一份数据只会制造 bug | 将来持久化非令牌的 UI 偏好需要另写几行 |

## 二、后端设计裁定

| 决定 | 为什么 | 代价 |
|---|---|---|
| 逻辑删除用**全局** `do_orm_execute` 监听器，而非在每个调用点显式安装过滤器 | 设计文档 §5.1 要求「全局过滤」。只在调用点安装的过滤器，任何一处忘记调用就是数据泄漏 | 想要看已删数据的会话必须显式调 `include_deleted()` |
| `install_soft_delete_filter(session)` 保留为幂等保险（语义诚实：确保监听器已挂载） | 计划要求这个函数名；导入即生效则让调用点不必依赖它 | 一个「看起来多余」的函数，已在 docstring 说明 |
| `sys_menu` **不设** `del_flag` | 菜单被删就该真消失，否则它的 `perms` 会残留在所有曾持有它的角色权限集里 | 删菜单不可逆 —— 而这正是种子/重置流程想要的 |
| 新增 `RemarkMixin`（`remark` 列）而非并入 `TimestampMixin` | 设计文档 §5.1 要求业务表有 `remark`，但纯追加的日志/会话表不该有备注列 | 每个类声明多一个 mixin |
| 四个复合主键关联表集中放 `models/associations.py` | 它们没有审计列、没有行为，分散到各自连接的模块里会把一个概念拆到四个文件 | 找 `sys_user_role` 要打开按「是什么」而非「连哪边」命名的文件 |
| 关系加载策略不对称：`SysUser.dept` 用 `joined`，`roles/posts`、`SysRole.menus/depts` 用 `selectin`；**不声明反向关系** | 认证路径需要 dept 与角色；反向的 `SysRole.users` 会让每次角色列表查询都把该角色所有用户拖出来 | 反向查询要显式 join |
| 令牌失败原因统一为同一条消息、同一个 401 | 区分「过期」与「伪造」等于白送一个探测预言机；前端也不需要区分，它依据状态码和有无 refresh 令牌判断 | 客户端无法提示「会话已过期」这类更具体的话术 |
| `hash_password` 超过 bcrypt 72 字节上限时抛错，而非静默截断 | 静默截断意味着两个不同的长密码可以认证同一个账号 | 违反契约的调用方得到 500 而非 422（已由 schema 的字节长度校验堵住） |
| `decode_token` 失败时用 `from None` | 让指明具体失败原因的 PyJWT 异常不进日志与堆栈 | 调试时少一层信息 |
| 缓存不引 Redis：`CacheBackend` 抽象 + 进程内 TTL 实现，且**不建后台清理任务** | 本机无 Redis，演示项目上它只增加启动复杂度；后台任务会活得比事件循环长，在「每个测试新建一个 cache」时制造噪音与串扰 | 写入后从不读取的键会驻留到下次 `set()` 触发清理；多 worker 部署时每个 worker 一份缓存（这才是该上 Redis 的临界点） |
| `incr` 全程持锁，且保留原有过期时间 | 登录失败计数会被并发命中，丢一次更新就等于账号提前解锁；保留原 TTL 则失败洪峰无法把锁定窗口无限推后 | 每次自增多一次加锁 |
| 登录顺序固定为 **验证码 → 锁定 → 凭据** | 验证码错误绝不能计入锁定，否则任何人知道用户名就能把该账号锁死 | 被锁定的账号仍需通过验证码才能发起尝试 |
| 已逻辑删除的账号返回与密码错误**相同**的消息 | Review Focus #1 在凭据路径上的应用：调用方学不到哪些账号存在 | 无法给出「账号已删除」这类提示 |
| 锁定检查先于凭据检查，正确密码在锁定期间同样被拒 | 否则锁定形同虚设 | 合法用户被锁期间即使输对也无法登录（设计如此） |
| `_dummy_password_hash()` 用 `lru_cache` 惰性计算 | 进程启动不必付一次 bcrypt cost-12 的开销；但不存在账号的登录仍消耗与真实账号相同的 bcrypt 时间（无可计时侧信道） | 第一次未知账号登录多付一次哈希成本 |
| 审计字段按列宽截断 | 超长 `User-Agent` 不能让「写审计日志」变成「登录失败」 | 超长输入在日志里被截断 |
| 新增 `CAPTCHA_ENABLED` 开关（计划未提，默认 `true`） | 验证码答案存在**服务端进程内存**里，任何独立的自动化客户端都读不到它 —— 不开关就无法对真实 HTTP 登录做端到端验证。RuoYi 也有等价能力，前端已带 `captcha_enabled` 字段 | 有人在内网/公网部署时关掉它会削弱登录防护；`.env.example` 已写明，默认值是安全的 |
| `LoginRequest` 的 `code`/`uuid` 只校验形状与长度，不要求必填 | 是否必填取决于运行时配置（`CAPTCHA_ENABLED`），那是验证码服务的职责，不是 schema 的。验证码启用时空 code 应得到服务的 400，而不是校验层的 422 —— 两者对客户端含义不同 | schema 少了一层保护，由服务层承担 |
| 菜单图标值统一为 Element Plus 组件名 | 前端通过 `<component :is="menu.meta.icon">` 渲染，只能解析真实组件名 | 后端种子数据带上了前端框架的命名约定 |
| 种子脚本改为**更新**既有菜单行的展示字段 | 否则「常量即事实来源」是假的：改了图标再跑一次种子会被静默忽略。刻意限定在展示字段，绝不覆盖密码或他人做过的决定 | 手工改过的菜单标题会被下一次种子运行还原（这正是意图） |
| `alembic/env.py` 支持 `config.attributes["sqlalchemy_url"]` 与 `-x db=<name>` | 测试套件需要在不改 `.env` 的前提下迁移测试库 | 两处 URL 解析分支 |

## 三、前端设计裁定

| 决定 | 为什么 | 代价 |
|---|---|---|
| 用官方脚手架 `create-vue --bare` 定版本，而不是凭记忆手写配置 | 版本组合由生态自身保证兼容（Vue 3.5 / Pinia 4 / Router 5 / Vite 8 / TS 6 / Vitest 4，均新于我的既有知识） | 需要实测确认每个 API 未被改动 |
| 请求层用**两个** axios 实例：`service`（带拦截器）与裸的 `refreshClient` | 让「刷新接口自身 401 又触发刷新」在结构上不可能，而不是靠一个可能被忘记检查的标志位 | 多一个实例要维护 |
| 副作用通过可注入的 `sessionHooks`（`notifyError`/`onSessionExpired`），不直接 import Element Plus 与 router | 测试可以直接断言 hook，而不必 mock UI 库；也避免 `request.ts` 引入 router 造成循环依赖 | 一层需要读者跟随的间接 |
| 授权测试独立成 `tests/test_authz.py`（计划要求追加进 `test_auth.py`） | 认证（你是谁）与授权（你能做什么）是两个关注点，混在一起改一个要通读另一个 | 两个文件而非一个 |
| `CurrentUser` 增加 `access_jti` 字段（计划接口未列） | 登出必须精确结束**当前这个**会话，需要被验证过的那个 jti；在登出路由里重新解码 token 等于重复一遍校验逻辑 | dataclass 多一个字段 |
| 把 `WILDCARD_PERM`/`ADMIN_ROLE_KEY` 移到 `core/constants.py`，`SESSION_REJECTED_MSG` 移到 `core/security.py` | `core/deps.py` 依赖 `services/auth_service`，若服务层再反向 import 就是真循环；而且 `core/` 依赖 `services/` 本身就是错误方向 | 无 |
| 新增 `utils/timeutil.py` 的 `utcnow()` | 两个模块都需要「与列类型匹配的 naive UTC」，第二处手写 `datetime.now(...).replace(tzinfo=None)` 就是两者开始漂移的起点 | 一个极小模块 |
| catch-all 路由**不放在** `generateRoutes` 里（计划要求放里面），而是独立的 `createCatchAllRoute()` + `appendCatchAll(router)`，由守卫在注册完动态路由后调用 | 计划的写法只能满足「catch-all 注册在最后」与「空菜单返回 `[]`」其中之一；放在守卫里还让**零菜单**的账号访问未知路径也能看到 404 页而不是白屏 | 多两个导出 |
| `constantRoutes` 只含 `/login` 与 `/404`（Layout 外壳在 Task 14 加入） | 保持每个提交自洽 | 中间一个提交里只有登录页可达 |
| 权限判定下沉为 `utils/permission.ts` 的纯函数，指令只是 DOM 移除的薄壳 | 同一个问题（此人能否做此事）被指令、布局、测试三处询问 | 一个小模块 |
| 针对 `src/views/**` 与 `src/layout/**` 关闭 `vue/multi-word-component-names`，并把 `Navbar.vue` 改名 `AppNavbar.vue` | 该规则本意是避免与 HTML 元素撞名；页面组件按路由命名，而 `index.vue` 不是风格选择 —— 后端下发的 `system/user/index` 要经 `import.meta.glob` 映射到文件，改名会打断这条链路。`Navbar` 则是真的过于泛化，与旁边的 `AppMain.vue` 不一致，应当改名 | 该规则仅对页面/外壳组件关闭 |
| 登录页在 Task 13 就完整实现（计划安排在 Task 15） | `routes.ts` 引用它，缺文件是**类型错误**而不是运行时意外；写个占位再替换只会让历史里多一个占位文件 | Task 15 变成纯验收任务 |
| 动态路由注册为**命名 Layout 路由的子路由**（`router.addRoute(LAYOUT_ROUTE_NAME, route)`） | 后端下发的顶层菜单路由自身没有组件；挂在 router 根层级时，子页面会渲染在布局**之外** —— 侧边栏、面包屑、标签页全部消失。这是浏览器验收实测发现的 | 需要给外壳路由命名 |
| Element Plus 图标在 `main.ts` 全量全局注册 | 侧边栏渲染的是运行时才知道的图标名（`meta.icon`），没有 import 语句可供自动生成 | 打包体积无法 tree-shake 图标 |
| 守卫用显式的 `hydrated` 标记判断是否已水合，而不是「roles 非空」 | 零启用角色的账号合法地拥有 `roles: []`，用它当哨兵会让守卫反复水合并重放同一次导航（评审实测：一次导航 32 次 profile 请求，生产构建下无限循环） | store 多一个字段 |
| 刷新成功后的**重放**不放在刷新的 `try` 里 | 重放遇到 500/403/超时都走「会话失效」分支会清空令牌、硬跳登录页，把用户踢出一个完全有效的会话 | 错误分支多一层判断 |
| 重放再次 401 时才结束会话 | 刚签发的令牌都被拒，说明服务端已不认这个会话 | 无 |

## 四、评审确认成立但本轮未修的问题（Deferred minors）

以下由整支分支的独立评审提出、我复核认可，但**刻意不在本轮修复**（P0 不阻塞，且改动会扩大提交范围）。
每条写清影响与建议时机，而不是假装已解决。

| # | 问题 | 影响 | 建议时机 |
|---|---|---|---|
| 1 | 设计文档 §5.1 与 README 承诺「`user_name`/`role_key`/`post_code` 的唯一性由 service 层在事务内校验」，代码里**不存在**这个校验 | P0 无创建接口所以产生不了重复；P1 一旦有用户/角色新增，就可能出现两条同名活记录，而 `_find_user` 会静默取第一条 | P1 用户 CRUD 落地**之前**必须补 |
| 2 | `PageParams` 目前是死代码（只有测试引用），没有任何路由消费它 | 「分页边界不会 500」只在模型层被证明，HTTP 层未验证 | P1 第一个列表接口落地时补 HTTP 层断言 |
| 3 | 设计文档 §5.5 称 `access_jti`/`refresh_jti` 唯一，迁移建的是**非唯一**索引；`refresh_tokens` 用 `db.scalar()` 取首行 | 碰撞概率极低，但文档与 schema 不一致 | 顺手对齐（加唯一索引或改文档） |
| 4 | `MemoryCache.incr` 不会触发 `_prune`，只有 `set` 会 | 只发验证码不写其它键时，过期条目不会被回收 | 低优先级；条目量级极小 |
| 5 | `sys_user_token` 只增不减：每次登录与刷新都插一行，重复登录不撤销旧会话，也没有清理任务 | 表持续增长；P1 的「在线用户」列表会变脏 | P1 在线用户功能落地时一并处理 |
| 6 | 导航守卫在 profile/routers **任何**失败时都调 `resetAll()` | 后端重启造成的一次瞬时 5xx 会把用户踢出登录、丢掉仍有效的 refresh 令牌 | 建议改为「保留令牌 + 提示 + 重试」 |
| 7 | `DEBUG` 默认 `true`，`init.ps1` 也写入 `DEBUG=true` | `/docs` 与未鉴权的 `/__test__/*`（含一个故意抛 500 的接口）默认全部开启 | 对外暴露前必须关；README 已就验证码给出同类提示 |
| 8 | `init.ps1` 用 `$ErrorActionPreference='Continue'`（计划要求 `Stop`）；第 20 行 `$ctl` 是 `$mysqlCtl` 的重复定义 | 前者是为绕开原生 stderr 的权衡；后者是死代码。副作用是非预期的 cmdlet 失败不会中断脚本 | 低优先级 |
| 9 | 多标签页同时刷新存在竞态：轮换没有宽限期，两个标签页读到同一个旧 refresh 令牌时后者会被强制登出 | 多标签页场景下用户可能被意外登出 | 可加「同一旧令牌短时间内复用视为合法」的宽限窗口 |
| 10 | `AppMain.vue` 的 `keep-alive :include` 取自 `view.closable`，而首页不可关闭 | 首页永不缓存，与注释「访问过的页面保持存活」不完全一致 | 低优先级 |
| 11 | 登录页预填 `admin` 并在页面上打印演示密码 `Admin@123456` | 仅适用于演示作品集 | 部署前必须去掉 |

## 五、独立评审的结论

- **无 Critical**；4 个 Important（已全部修复，见 `P0验收记录.md` 第六节）；8 个 Minor（见上表）。
- 评审者独立复跑了后端与前端测试套件、`vue-tsc`/`oxlint`/`eslint`/`vite build`、两个库的
  `alembic check`，并核对了验收记录的逐文件测试数量（结论：准确）。
- 评审者用**独立探针**复现了两个我未覆盖的缺陷（零角色账号的无限重定向、重放非 401 导致会话销毁），
  并指出我自己的测试辅助函数 `rotatingResponder({secondStatus})` 正是为此写的却从未被使用。
- 评审者判定 4 条文档声明「虚假或夸大」，我**接受并修订了文档**而不是辩解：
  Review Focus #4 被限定为仅在模型层覆盖、#2 的「重建同名」被限定为仅 ORM 层、
  验收记录的 HEAD 锚点与它自己描述的内容不一致。
- 评审者报告的一处「无法解释的异常」（首次后台 `pytest` 出现 122 个 fixture 级
  `sqlalchemy.exc.OperationalError`）其实有解释：那段时间我为验证「真实数据库故障不泄漏」而停掉了
  MySQL。不是偶发故障。
