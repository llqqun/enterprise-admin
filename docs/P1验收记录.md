## 四、验收中发现并修复的缺陷

浏览器验收的价值在这一轮体现得很直接：**三个缺陷里有两个是单元测试与类型检查都抓不到的**。

### 4.1 用户管理页：辅助请求失败导致主列表根本不加载（严重）

`onMounted` 原本是：

```ts
const [tree, roles] = await Promise.all([deptTreeSelect(), listRoles({...})])
deptTree.value = tree
roleOptions.value = roles.rows
await fetchList()
```

`manager` 只有 `system:user:list`，没有 `system:dept:list` / `system:role:list`。两个辅助请求
返回 403 → **整个 `Promise.all` 抛错 → `fetchList()` 从未执行**。结果是页面显示
「当前账号可见 **0** 个用户」并弹两个「没有操作权限」。

这不是权限生效，而是**页面在撒谎**：同样的账号直接调 `/api/v1/system/user` 明明能拿到 2 行。

修复：辅助数据不再是主列表的前置条件，按权限码决定要不要请求，失败也只降级为空选项：

```ts
if (hasPermission(userStore.perms, ['system:dept:list'])) {
  deptTree.value = await deptTreeSelect().catch(() => [])
}
if (hasPermission(userStore.perms, ['system:role:list'])) {
  roleOptions.value = await listRoles({...}).then((d) => d.rows).catch(() => [])
}
await fetchList()   // 无论如何都执行
```

修复后同一账号看到 2 个用户（见 3.2 截图）。

### 4.2 仪表盘上的一句过时文案

首页原本写着「用户/角色/菜单/部门/岗位等业务页面属于 P1，因此这些菜单项目前会落到 404 页」。
五个页面上线后这句话变成假的。改为说明当前账号的菜单与按钮由权限码决定。

### 4.3 构建门禁：`vue-tsc --build` 通过 ≠ 能构建

本轮之前（第 12 轮）出现过「只跑 type-check 就提交，结果 `vite build` 失败」的情况。
此后前端门禁一律以 **`npm run build`** 为准，本轮两个页面一次通过。

### 4.4 Element Plus 没有配置中文 locale（界面中英混排）

点开任意删除确认框，按钮是 **`Cancel` / `OK`**，而界面其余部分全是中文。原因是 `main.ts` 从未
给 Element Plus 配 locale，组件自带文案保持默认英文（分页的 `per page`、日期选择器等同样受影响）。

修复：在 `App.vue` 外层套 `el-config-provider :locale="zhCn"`（用 config-provider 而不是
`app.use(ElementPlus)`，是为了不放弃 unplugin 的按需导入）。修复后确认框为「取消 / 确定」。

这个缺陷**只有真的点开一次确认框才看得见** —— 静态检查、单元测试、甚至「页面能渲染」的检查都不会报。

|---|---|
| 在用户页新建一个用户 | 操作日志页出现 1 条：模块=用户管理、类型=新增、操作人=admin、方式=POST、URL=/api/v1/system/user、IP=127.0.0.1 |
| 再删除该用户 | 变成 2 条，新增与删除各一条，删除那条的 URL 是 `/api/v1/system/user/6` |
| 控制台错误 | 0 |

**最要紧的一条断言（查库验证）**：

```
oper_param = {"user_name": "logged_qa", ..., "password": "***", ...}
SELECT COUNT(*) FROM sys_oper_log WHERE oper_param LIKE '%<真实密码>%'  →  0
```

请求体里的密码在后端写入时就被替换成 `***`，且**逐层递归**处理嵌套结构 —— 只处理第一层会让
`{"user": {"newPassword": ...}}` 这类载荷漏出去。页面不做二次脱敏：如果展示层还得补救，
说明后端漏了，那是要修后端的事。

另外两条设计取舍：

- **失败也留痕**：`BusinessException` 会被记成 `status=1` 并带上 `error_msg`，然后原样抛给调用方。
  只记成功的日志回答不了「谁尝试了什么」。
- **写日志绝不能影响业务**：记录环节的任何异常都被吞掉并降级为一条 warning —— 审计重要，
  但不值得用「记不上就 500」去换。
- **删除/清空本身留痕**：先删，再写一条 `delete_oper_logs` / `clean_oper_logs` 的记录，
  这样「谁清掉了审计」永远查得到。删除权限单独一个码（`monitor:operlog:remove`），
  能看日志不等于能删日志。

### 5.11 在线用户（第 25 轮）

数据基础 `sys_user_token` 从 P0 起就在，但一直没有读它的接口。

| 项 | 结果 |
|---|---|
| 列表 | 浏览器实测 **10 个活动会话**（就是这些天真实登录累积的），列出账号/昵称/IP/浏览器/系统/登录时间/有效期 |
| 强制下线 | 选一个 `curl` 的旧会话 → 确认 → 提示「已强制下线」，**计数 10 → 9** |
| 控制台错误 | 0 |

三个设计取舍：

- **「在线」的判据是 refresh 未过期且未撤销**，不是 access —— access 只有 30 分钟，用它判断会把
  一个仍在用系统的人显示成离线。
- **强退是真的撤销那个会话**，所以被强退的人下一次请求会 401（有测试直接断言这一点），
  而不是「页面上看不见了但还能继续操作」。
- **不能强退自己的会话**：那等于用强制手段把自己踢出去，而退出登录就在手边。

顺带解决了一条 P0 时期的遗留（「`sys_user_token` 只增不减」）：登录时清理**该账号**已经彻底失效
（refresh 也过期）的行。按用户清理是有界的，不需要后台任务 —— 而引入后台任务正是 P0 刻意避免的事。

### 5.12 字典（第 26–27 轮）

两张表：类型（一组选项的名字）与数据（其中一个选项）。拆开是有意的 —— 一个类型可以在还没有
任何选项时就存在，而选项的排序/停用不该牵动类型。

浏览器实测（`admin`）：

| 项 | 结果 |
|---|---|
| 类型列表 | **3 条**（用户性别 / 通用状态 / 是否），状态列由 `DictTag` 渲染成「正常」 |
| 数据抽屉 | 点「数据」→ 抽屉标题「字典数据 —— 用户性别（sys_user_sex）」，3 条：男/0、女/1、未知/2 |
| 控制台错误 | 0 |

实现上值得记的三点：

- **`DictTag` 渲染的是字典里的标签与颜色**（`tag_type`），不是硬编码的映射表。所以新增一个状态值时
  不需要改任何前端代码 —— 这也让「字典」这个模块真的有存在意义，而不是一张只给人看的表。
- **改类型的 `dict_type` 会级联迁移数据行**（`sys_dict_data` 按字符串关联，没有外键）。前端在保存后
  调用 `invalidateDict()` 清缓存，否则别的页面还显示旧标签。
- **字典查询只要求登录**（`GET /system/dict/data/type/{type}` 不要 `system:dict:list`）：
  每个页面都可能要渲染状态标签，而一个只能看订单的人也得把 `0` 显示成「正常」。停用的类型返回空。

种子数据里预置了这三个字典（`DICTS` 常量），所以新环境装完就能看到内容，不是空页面。

### 5.13 参数设置（第 28 轮）

| 项 | 结果 |
|---|---|
| 列表 | **3 条内置参数**（验证码开关 / 注册开关 / 系统标题），类型列显示「内置」 |
| 控制台错误 | 0 |

核心语义：**「内置」= 不可删除，不等于不可修改**。参数表存在的意义就是能改值；而删掉一个内置键
并不会「关闭」某个功能，只会让读取方落到自己的兜底值 —— 行为被悄悄改变，页面上看不出异常。
删除被拒时后端会**点明是哪一个键**（只说「不允许删除」会让运维一个个去试）。

另外 `GET /system/config/configKey/{key}` 只要求登录：读一个开关的值不该需要「参数管理」权限。

**必须说清的局限**：这一轮只做了「存 + 管 + 读接口」。目前**没有任何业务代码通过它读配置**
（例如验证码开关仍走 `.env` 的 `CAPTCHA_ENABLED`）。把某个配置真正接进业务行为是后续的事 ——
在做到之前，不能把「参数设置」说成「可以动态开关功能」。

### 5.14 服务监控（第 29 轮）

| 项 | 结果 |
|---|---|
| CPU / 内存 / 交换 | 三个仪表盘分别显示 **0% / 79% / 1%**（实测值） |
| 磁盘 | 6 个挂载点，含文件系统与占用进度条 |
| 运行时 | Python 版本、操作系统、主机名、进程号、已运行时长、启动时间、进程内存、线程数 |

| 控制台错误 | 0 |

两个值得记的点：

- **CPU 必须有采样窗口**。`psutil.cpu_percent()` 不传 `interval` 时返回「自上次调用以来」的占用率，
  第一次调用永远是 `0.0` —— 一个永远显示 0% 的监控页比没有更糟。这里用 `interval=0.1`，
  并有一条测试直接度量 `collect()` 的耗时，确保这个窗口没有被改回去。
- **`psutil` 从 P0 起就在 requirements 里，但一直没有代码导入它**；这一轮它才真正被用到。

浏览器验收抓到一个视觉缺陷：仪表盘原本用 `:status` 控制颜色，而 Element Plus 在设置了 `status` 时

数字回来了。这种问题类型检查、构建、单元测试都不会报。

### 5.15 通知公告（第 30 轮）

| 项 | 结果 |
|---|---|
| 公告列表 | **2 条**（本周六停机维护/通知/已发布、欢迎使用 enterprise-admin/公告/已发布） |
| 首页「最新公告」 | 卡片出现，两条标题与列表一致 —— `/notice/latest` 有了真实消费者 |

核心语义：`status` 是**已发布 / 已撤回**，不是启用 / 停用。撤回的公告必须从首页消失，
否则撤回只是个装饰性字段（有测试断言这一点）。`/latest` 只要求登录 —— 首页要展示公告，

### 5.16 文件上传（第 31 轮）

| 步骤 | 结果 |
|---|---|
| 界面选一个 `.txt` 上传 | 提示「upload-probe.txt 上传成功」，列表 0 → 1 |
| **查库** | `original_name=upload-probe.txt`、`stored_name=8c4f…txt`（uuid）、`storage_path=2026/10/20/8c4f…txt`、`size=34` |
| **查磁盘** | `backend/uploads/2026/10/20/8c4f…txt`（34 字节）—— **客户端文件名没有被用作路径** |
| 删除 | 提示「删除成功」，列表回到 0 |
| **查磁盘 / 查库** | uploads 下 0 个文件；记录仍在且 `del_flag=2` |

安全规则逐条有测试：

- **扩展名白名单**（不是黑名单）：`.png/.jpg/.pdf/.txt/.md/.csv/.doc/.docx/.xls/.xlsx/.zip`。
  刻意排除 `.svg`/`.html`/`.js`（能在本站源执行脚本）与 `.exe`/`.ps1`（可执行）。
- **绝不用客户端文件名做路径**：存储名是 `uuid4().hex + 扩展名`。测试用 `../../evil.png` 上传，
  断言落盘路径不含 `..`、存储名不含 `/`。
- **双扩展名按最后一段处理**：`shell.php.png` 是 png，作为 png 下发就安全；
  按 php 处理才是漏洞。
- **下载强制 `attachment` + `nosniff`**：否则上传的 `.html` 会在本站源里渲染成 XSS。
- **MIME 由服务端映射**，不采信客户端的 `Content-Type`。
- **大小上限在读取后校验**，不依赖 `Content-Length`。

`StorageBackend` 抽象（设计文档 §5.6）也在这里落地：`LocalStorage` 会把每个键解析到单一根目录
**之下**，越界直接抛错而不是「清理路径」—— 一个没校验的 `..` 就是一个任意写原语。

### 5.17 个人中心：改自己的资料与密码（第 32 轮）

导航栏用户下拉 →「个人中心」，弹窗两个页签（资料 / 修改密码）。浏览器实测：页签与 8 个字段
（账号/昵称/邮箱/手机号/性别 + 原密码/新密码/确认新密码）都正常渲染。

两条安全规则，各有测试：

- **字段白名单**。`PUT /auth/profile` 只接受昵称/邮箱/手机/性别。测试里故意多传
  `user_name`、`status`、`dept_id`、`role_ids`，断言**一个都不生效** ——
  自助接口如果接受 `dept_id`，用户就能把自己挪进另一个部门从而扩大数据权限；
  接受 `status` 就能自己启用一个被停用的账号。
- **改密码要原密码，且只撤销其它会话**。不校验原密码的话，一个被劫持的会话就能把账号锁成
  自己的；而改密码最常见的动机是「旧密码可能泄露」，这时把别人留在登录态里等于白改。
  测试用两个会话验证：A 改密码后 A 仍可用，B 立刻 401。

另外「没传」与「传 null」被区分开了（`model_fields_set`）：只想改昵称的请求不会顺手清空邮箱。
