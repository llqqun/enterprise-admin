# enterprise-admin 面试讲解手册

> 事实基准：本仓库 `feat/p0-foundation` 分支（当前 HEAD `97a1050`，工作区干净）。
> 本文只写仓库里查得到的东西；路径、函数名、测试名都按原样保留，凡是 P1/P2 一律标出来。
>
> 这份手册的用法不是"背事实"，而是**背结构**：每条都按同一个四段模板说，说完就停。
> 项目已经因为"文档夸大覆盖范围"被独立评审纠正过一次（见 `docs/P0验收记录.md` 开头），
> 在面试里被抓住一次同样的错，代价比少讲一个功能大得多。

## 0. 怎么用这本手册

### 0.1 四段模板（每条技术点都按这个顺序说）

| 段 | 内容 | 时长 |
|---|---|---|
| ① 一句话答案 | 先给结论，不给背景。对方只给你 20 秒时就靠这一句 | 5–10 秒 |
| ② 30 秒结构化回答 | 3–4 拍，每拍一句话。这是**反啰嗦装置**：拍数固定，说完就停 | 30–40 秒 |
| ③ 仓库证据 | 文件、函数、测试名。把"我说了"变成"这行代码在哪儿" | 10–20 秒，通常等追问再说 |
| ④ 追问与短答 | 预判下一问，每个答案 1–3 句 | 按需 |

### 0.2 说话纪律（针对你自己总结的"想到哪说到哪"）

1. **先给结论再给理由**。第一句永远是判断句（"是的，已实现"／"没有，属于 P1"），不是铺垫。
2. **报数**。"三点""两个取舍""四层"，让对方知道你要说几条；说满就停。
3. **每拍一句话**。拍内不要嵌套新话题；想展开的细节留到追问。
4. **被打断就停在那一拍**，不要从第一拍重讲。
5. **不会就说不会**，用固定话术（见 §0.5），然后补一句"这是我接受的代价"或"下一步我会怎么做"。

### 0.3 红线：这三件事，永远不要说成"做了"

| 不能说 | 必须说 |
|---|---|
| "四层权限都实现了" | 接口级、菜单/路由级、按钮级已实现；**数据级（`data_scope` 行级过滤）是 P1** |
| "测试覆盖很全" | 后端 130 项、前端 40 项，覆盖认证/授权/缓存/菜单/响应/迁移与前端请求层、store、指令、守卫；**没有界面组件测试、没有 E2E** |
| "唯一性有数据库保证" | 业务键**故意不建唯一索引**；service 层校验是设计文档承诺、**P0 尚未实现**，P1 用户 CRUD 落地前必须补 |

### 0.4 现场演示动线（3 分钟，按顺序做，别乱点）

1. `start.ps1` 已启动 → 打开 `http://127.0.0.1:5173`，用 `admin / Admin@123456` 登录。
2. 侧边栏 14 项（系统管理 8 子项 + 监控中心 4 子项）→ 说明菜单来自 `GET /api/v1/auth/routers`，不是前端硬编码。
3. 退出，换 `manager / Manager@123` 登录 → 侧边栏只剩 4 项（用户管理、在线用户）。**这是四层权限里第②层的活体证据**。
4. 退出，换 `staff / Staff@123` 登录 → 侧边栏 0 项，显示"当前账号没有任何菜单权限"，页面不白屏、控制台 0 error。
5. 直接访问 `http://127.0.0.1:5173/system/user` → 面包屑、标签页、菜单高亮都在（说明动态路由挂在了 Layout 子路由下）。
6. 打开 `http://127.0.0.1:8000/docs` → 7 条接口（6 条 `/api/v1` + `/health`）。

> 点菜单进 404 是**预期行为**：业务页面属于 P1，`generateRoutes` 找不到组件会降级到 404 页并打
> `[permission] no view found for component "system/user/index"` 警告，不白屏。

### 0.5 "不会"的标准话术（三句）

1. "这块我**没做到**，不是没想过——它属于 P1，原因是……"
2. "如果你问的是实现细节，我说不清；我清楚的是**边界**：P0 做到哪、P1 该从哪儿开始。"
3. "这是我**接受的代价**，当初的判断是……如果重来一次我会……"

6. **现在到哪**："P0 已交付并验收，P1-A 的计划也写好了：数据权限 + 部门/岗位/菜单/角色/用户 CRUD，
   目标是让 S2（两个角色看到的菜单、按钮、数据行数都不同）成为可现场演示的事实。"

### 1.4 "你具体做了什么"的 1 分钟版（3 拍）

1. **我定的架构**："分层规则是 `api → services → models`，横切能力全在 `core/`；
   我写了一条可复核的规则：`api/v1/` 里不允许出现 `select(`/`text(`，`services/` 里不允许 `import fastapi`——
   我已经实际 grep 过，两处都是零命中。"

3. **我留下的证据**："每一条都能在 `docs/架构设计.md`、`docs/数据库设计.md`、`docs/接口清单.md` 里
   找到对应的代码位置；P0 未实现的能力就写在它本该出现的位置，不塞脚注。"

### 2.2 为什么是 FastAPI，不是 Django / Flask

**① 一句话答案**："我要的是一套能自动产出接口文档、并且拿 schema 当契约的框架，FastAPI 天生就是这个形状；
Django 自带的东西我大部分不需要，Flask 则什么都不给。"

**② 30 秒结构化回答**

1. **校验和文档是一件事**：`LoginRequest` 一个 Pydantic 模型同时管入参校验、422 错误结构、`/openapi.json`，不用维护第二份文档。
2. **依赖注入正好对上权限模型**：`require_perm("system:user:add")` 是个依赖，声明在路由上，权限检查与业务代码不混。
3. **Django 的代价**：它自带 ORM/Admin/模板/中间件，但我这个项目是前后端分离的 REST 服务，这些是负担而不是资产。
4. **Flask 的代价**：异步、校验、依赖注入、文档都得自己拼装，拼出来的东西不如 FastAPI 原生一致。

**③ 仓库证据**：`backend/app/schemas/auth.py::LoginRequest`、`backend/app/core/deps.py::require_perm`、
`backend/app/main.py::create_app`（`docs_url`/`redoc_url`/`openapi_url` 由 `settings.DOCS_ENABLED` 控制）。

**④ 追问与短答**

- **Q：为什么不用 Django REST Framework？** A：DRF 的 serializer 是另一套 DSL，我更喜欢"校验模型本身就是文档"这一条链；另外异步在 DRF 里不是一等公民。
- **Q：FastAPI 0.143 这么新的版本，你不怕坑？** A：版本不是我选的，是 pip 解析完锁进 `requirements.lock.txt` 的，然后每条链路我都实际启动验证过——这是"不接受理论上兼容"的原则。
- **Q：FastAPI 有什么你踩过的坑？** A：缺失 `Authorization` 头时它默认返回 `{"detail": "Not authenticated"}`，不是我的信封，所以 `OAuth2PasswordBearer` 我设了 `auto_error=False`，自己抛 `UnauthorizedException`。
- **Q：那这不是更绕吗？** A：绕一层换的是"所有错误都长同一个形状"，前端只需要一套解析逻辑。

### 2.3 为什么 ORM 用 async SQLAlchemy，而不是同步

**① 一句话答案**："既然选了 ASGI，就用异步驱动把它跑满；同步驱动在 async 端点里会占住事件循环的线程池，
203 条接口铺开之后就是瓶颈。"

**② 30 秒结构化回答**

1. **驱动一致**：`mysql+asyncmy` + `create_async_engine` + `AsyncSession`，`get_db` 本身就是 `async def` 依赖。
2. **异步下的真实坑我踩了**：隐式懒加载会抛 `MissingGreenlet`，所以 `SysUser.dept` 用 `lazy="joined"`、`roles/posts` 用 `lazy="selectin"`。
3. **事务边界统一**：`get_db` 正常 `commit()`、异常 `rollback()`、`finally` 关会话，端点函数里不写事务管理。
4. **代价**：异步 ORM 的报错比同步难读，且不能随手用同步的 `session.query()`。

**③ 仓库证据**：`backend/app/db/session.py::get_db`（`pool_pre_ping=True`、`pool_recycle=3600`）、
`backend/app/models/user.py`（三个关系的 `lazy` 策略，注释写明 `MissingGreenlet`）、
`backend/tests/conftest.py`（`NullPool` + `join_transaction_mode="create_savepoint"`）。

**④ 追问与短答**

- **Q：为什么 `NullPool`？** A：pytest-asyncio 每个用例一个事件循环；在一个循环里创建的池化连接不能带到下一个循环用。
- **Q：为什么不用 SQLite 测？** A：拿 SQLite 测 MySQL 的行为等于没测——JSON、字符集、排序规则、递归 CTE 都不同。测试跑在独立的 `enterprise_admin_test` 库上，每用例一个事务并回滚。
- **Q：`pool_recycle=3600` 为什么？** A：MySQL 默认 `wait_timeout` 8 小时会掐掉空闲连接，配合 `pool_pre_ping` 先探活再交付。
- **Q：asyncmy 编译不了怎么办？** A：计划里已备案回退 `aiomysql`（纯 Python），只改 URL 前缀；实际本机有 cp312 wheel，没用上这条回退路径。

### 2.4 为什么 MySQL 用便携版，而不是 Docker

**① 一句话答案**："这台机器根本没有 Docker，而且便携版恰好满足我的硬约束：不写 C 盘、不注册 Windows 服务、删目录即卸载。"

**② 30 秒结构化回答**

1. **约束**：我没有 Docker、没有 WSL；MySQL 官方 MSI 会写 C 盘并注册系统服务，两条都违反约束。
2. **选型**：8.0.29 winx64 ZIP 解压到 `D:\devtools\mysql-8.0.29`，数据目录 `D:\devtools\mysql-data`，日志 `D:\devtools\mysql-logs`。
3. **功能够用**：utf8mb4、JSON、窗口函数、**递归 CTE**——后者正是 P1 数据权限"本部门及以下"要用的。
4. **代价**：8.0.29 是 2022 年的版本，不是当前 LTS；有容器环境时换 8.4。

**③ 仓库证据**：`tools/install-mysql.ps1`（生成 `my.ini`、`--initialize-insecure`）、`tools/mysql-ctl.ps1`（start/stop/status）、
`docs/P0验收记录.md` §四 D 盘落位审计、`docs/P0决策记录.md` §一（日志改到 `mysql-logs` 而不是设计文档写的 `mysql-data\logs`，
原因是 datadir 内任何文件都会让初始化以 MY-010457 中止）。

**④ 追问与短答**

- **Q：日志目录为什么不在 datadir 里？** A：我在真实初始化时踩到了 MY-010457——datadir 里出现非数据文件会让 `--initialize-insecure` 直接中止。这条写进了决策记录，因为我判断错了一次。
- **Q：8.0.29 有什么风险？** A：安全补丁落后于 8.4；功能上我没有用到 8.4 才有的特性。
- **Q：为什么不用 MariaDB / SQLite？** A：MariaDB 与 MySQL 有行为差异、面试口径上也不是 MySQL；SQLite 的字符集、并发、排序规则与需求不符。
- **Q：时区你怎么处理的？** A：应用写 naive UTC（`app/utils/timeutil.py::utcnow`），库端 `my.ini` 设 `default-time-zone='+00:00'`。两边不一致的话，同一行里 `create_time`（服务端 `now()`）和 `access_expire`（应用写入）会处在不同时区，这类 bug 几个月后会以"过期令牌仍然有效"的形式浮出来。

### 2.5 为什么不上 Redis；什么时候非上不可

**① 一句话答案**："P0 的缓存需求只有验证码和登录失败计数，上一套 Redis 只是给演示环境加一个启动依赖；
但我留了 `CacheBackend` 协议，换成 Redis 是加一个类 + 改一行。"

**② 30 秒结构化回答**

1. **抽象先行**：`CacheBackend`（get/set/delete/exists/incr/clear）+ `MemoryCache`，模块级单例 `cache`。
2. **真实用量**：`captcha:{uuid}`（TTL 120 秒）、`login_fail:{归一化账号}`（TTL 600 秒）——就这两个。
3. **实现细节**：惰性过期、`incr` 全程持锁且保留原 TTL（登录失败计数会并发命中，丢一次更新等于账号提前解锁）；**刻意不建后台清理任务**。
4. **临界点**："多 worker"就是那个临界点：两个 uvicorn worker 各持一份缓存，验证码会互相查不到、5 次锁定会变成每个 worker 各 5 次。

**③ 仓库证据**：`backend/app/core/cache.py`（文件头 docstring 直接写了"That is the point at which Redis stops being optional"）、
`backend/tests/test_cache.py::test_incr_is_atomic_under_concurrency`（50 次并发自增断言等于 50）、
`docs/架构设计.md` §9.3。

**④ 追问与短答**

- **Q：为什么不做后台清理任务？** A：后台任务会活得比事件循环长，而测试里每个用例都会新建一个 cache——它带来的串扰比回收的内存更贵。
- **Q：那你现在多 worker 跑过吗？** A：**没有**。`start.ps1` 起的是单个 uvicorn 进程（不带 `--workers`），所以这是一个**未验证项**，不是我声称的性质。要上多 worker，我先把 `RedisCache` 做掉。
- **Q：`incr` 持锁会不会有性能问题？** A：这是每个进程内一把 `asyncio.Lock`，只保护一次字典读改写；跟 bcrypt cost-12（每次登录几十毫秒）比可以忽略。
- **Q：验证码为什么要能关？** A：验证码答案存在服务端进程内存里，任何自动化客户端读不到——不提供 `CAPTCHA_ENABLED=false` 这个开关，就无法对真实 HTTP 登录做端到端测试。默认值是安全的 `true`。

### 2.6 为什么状态管理用 Pinia，不用 Vuex

**① 一句话答案**："Pinia 是 Vue 3 官方推荐的默认方案，而且它的 setup 语法写法和我写的组合式代码是同一个形状。"

**② 30 秒结构化回答**

1. **官方口径**：Vue 3 的新项目文档直接推荐 Pinia，Vuex 处于维护状态。
2. **写法一致**：`defineStore('user', () => {...})` 里就是 `ref`/`computed`/函数，跟组件里的写法一样，没有 mutation 那一层。
3. **类型友好**：`useUserStore().perms` 能直接推出类型，不需要为 Vuex 的字符串 mutation 写额外类型。
4. **代价**：生态里 Vue 2 时代的示例大多是 Vuex 写法，团队迁移时得换个脑子。

**③ 仓库证据**：`frontend/src/stores/{user,permission,app,tagsView}.ts` 全部是 setup 风格；
`frontend/src/stores/__tests__/user.spec.ts`（6 项）测试里直接 `setActivePinia(createPinia())` 就能跑，不需要挂 Vue 实例。

**④ 追问与短答**

- **Q：Pinia 里你怎么处理"未水合"？** A：`useUserStore.hydrated` 是一个独立的布尔标记，**不是**"roles 非空"——零角色账号合法地拥有 `roles: []`，用后者当哨兵会导致无限重定向（评审实测一次导航 32 次 profile 请求）。
- **Q：状态持久化用什么？** A：没有用 `pinia-plugin-persistedstate`。令牌的读写集中在 `utils/auth.ts` 的 `getAccessToken/setTokens/removeTokens`。理由：计划里本来列了这个插件，但令牌存放位置已经被显式接口决定了，再叠一套隐式持久化持久化同一份数据只会制造 bug。
- **Q：为什么 `stores/counter.ts` 还在？** A：那是 `create-vue` 脚手架的示例残留，**没有任何代码引用它**（我 grep 过）。我没删是因为它在脚手架的测试基线里，但如果你在我仓库里看到它，它就是这个来源，不是设计选择。
- **Q：Vue 2 的 Vuex 经验怎么迁移？** A：心智是一样的：单一状态源 + action 管异步 + getter/computed 管派生。差异是 Pinia 取消 mutation，直接改 state；以及每个 store 是独立模块，不再有一个 root store。Vue 3 我还在补，这块我承认不如 Vue 2 熟。

## 3. 四层权限模型

### 3.1 一条主线（先给这张表，再讲任一层）

| ① 接口级 | **已实现** | `backend/app/core/deps.py::require_perm` |

### 3.2 第①层：接口级权限 `require_perm`

**① 一句话答案**："`require_perm("system:user:add")` 是挂在路由上的依赖：超管直接放行，否则比对权限码集合，不匹配抛 403。"

**② 30 秒结构化回答**

1. **判定顺序**：`current.is_admin or "*:*:*" in perms or perm in perms` → 通过；否则 `logger.info` 记下"谁想干什么被挡住"并抛 `ForbiddenException`。
2. **超管为什么是特例**：`is_admin` 由角色 key `admin` 决定（`ADMIN_ROLE_KEY`），不走权限码比对——避免新增功能后管理员被自己的权限系统锁死。
3. **权限码从哪来**：`get_current_user` 把用户每个**启用角色**的每个**启用菜单**的 `perms` 收进集合；超管直接给 `{"*:*:*"}`。
4. **同一份数据**：`build_profile` 下发的 `permissions` 就是 `require_perm` 检查的那个集合（超管下发 `["*:*:*"]`），所以前端隐藏的按钮与后端放行的调用按构造一致。

**③ 仓库证据**：`backend/app/core/deps.py::require_perm`、`::_permission_codes`、`backend/app/core/constants.py`（`ADMIN_ROLE_KEY`、`WILDCARD_PERM`）、
`backend/app/services/auth_service.py::build_profile`、
测试 `tests/test_authz.py::test_admin_bypasses_the_permission_check`、`::test_non_admin_without_the_permission_gets_403`、`::test_non_admin_with_the_permission_passes`。

**④ 追问与短答**

- **Q：403 为什么用 `logger.info` 而不是 `error`？** A：403 是正常事件，不是故障；但"谁想做什么被挡住"正是排查用户投诉时要的信息，所以带上权限码记 INFO。
- **Q：`is_admin` 用角色 key 字符串判断，硬编码？** A：是硬编码，也是有意的：`ADMIN_ROLE_KEY = "admin"` 是唯一一个按 key 而不是按权限码判断的地方，为的是防止管理员自锁。这也是 RuoYi 系的通行做法。
- **Q：权限码变化了怎么办？** A：每次请求都重算 `perms`，没有缓存，所以角色/菜单一改，下一个请求就生效。
- **Q：那性能呢？** A：每个认证请求会多几条查询（会话行、用户 + `selectin` 角色与菜单）。P0 没有做缓存——设计文档 §5.5 说"用缓存吸收开销"，`grep` 确认 `deps.py` 里没有 `cache` 引用，**这是一个未兑现的设计意图**，我如实标出来。

### 3.3 第②层：菜单/路由级

**① 一句话答案**："后端按登录用户的角色实时查菜单树，前端把它翻译成路由再 `addRoute`，侧边栏和路由用的是同一份数据。"

**② 30 秒结构化回答**

1. **后端**：`GET /api/v1/auth/routers` → 过滤 `menu_type IN ('M','C')`、`status='0'`；非超管再 JOIN `sys_role_menu` / `sys_user_role` / `sys_role`（并要求 `sys_role.status='0'`），排序 `parent_id, order_num`，`.unique()` 去重。
2. **前端**：`import.meta.glob('../views/**/*.vue')` 把后端的组件字符串（`system/user/index`）映射成真实组件；`router.addRoute(LAYOUT_ROUTE_NAME, route)` 注册为 Layout 的**子路由**。
3. **兜底路由必须在动态路由之后**：`appendCatchAll(router)` 是独立一步，不是埋在循环里的一行——注册早了会把所有动态路由都吃掉。
4. **注册完必须重放导航**：`return { path: to.path, ... }`，否则 vue-router 已经判定目标未知，页面会渲染 404。

**③ 仓库证据**：`backend/app/services/menu_service.py::_visible_menus`、`::_to_route`、`::get_routers`；
`frontend/src/stores/permission.ts`（`viewModules`、`resolveComponent`、`createCatchAllRoute`、`appendCatchAll`）；
`frontend/src/router/guard.ts`（`hydrated` 判断、`addRoute`、`appendCatchAll`、重放）；
测试 `backend/tests/test_menu.py`（15 项，含 `::test_routers_node_shape`、`::test_routers_excludes_button_nodes`）、
`frontend/src/stores/__tests__/permission.spec.ts::matches an unknown path only after the dynamic routes are registered`、`frontend/src/router/__tests__/guard.spec.ts`（4 项）。

**④ 追问与短答**

- **Q：为什么挂在 Layout 子路由，不挂在根？** A：后端下发的顶层菜单路由自己没有组件，挂在根层级时子页面会渲染在布局**之外**——侧边栏、面包屑、标签页全消失。这是浏览器验收实测发现的。
- **Q：零权限用户会白屏吗？** A：不会。`get_routers` 返回 `[]` 且是 **200 不是错误**，前端 `generateRoutes([])` 得到 `[]`，侧边栏显示"当前账号没有任何菜单权限"。活体证据是 `staff` 账号（`docs/P0验收记录.md` §二）。
- **Q：`sys_menu.visible='1'` 的隐藏菜单会下发吗？** A：**会**。`_to_route` 只是把它翻译成 `hidden: true`，SQL 里**没有** `visible` 过滤——"隐藏菜单不下发"这个直觉是错的，种子数据全是可见所以观察不到差异。这一条我写在架构文档 §6.2 里，P1 的菜单管理接口要明确它。
- **Q：菜单被删了但角色的权限码还在？** A：这正是 `sys_menu` **不设 `del_flag`** 的原因——菜单删除是物理删除，否则它的 `perms` 会永远留在所有曾持有它的角色权限集里。代价是删菜单不可逆。
- **Q：停用角色的菜单还会下发吗？** A：不会。这是评审发现并修掉的一个 Important：接口层和 profile 层都忽略停用角色，唯独菜单层当时没 join `sys_role`，同一个账号在不同层得到矛盾答案。回归测试是 `test_menu.py::test_routers_exclude_a_disabled_role`、`::test_routers_exclude_a_soft_deleted_role`、`::test_routers_still_return_menus_for_a_normal_role`。

### 3.4 第③层：按钮级，以及"隐藏按钮不是拦截"

**① 一句话答案**："`v-hasPerm` 在元素挂载时检查权限码，不匹配就把它从 DOM 移除——它只是体验优化，**真正的拦截在第①层**。"

**② 30 秒结构化回答**

1. **指令做什么**：`mounted` 里调 `hasPermission(userStore.perms, required)`，为假就 `el.parentNode.removeChild(el)`。
2. **判定下沉**：真正的判断在 `utils/permission.ts` 的纯函数 `hasPermission`——同一个问题（此人能否做此事）被指令、布局、测试三处询问，只有一份实现；空数组视为"不需要权限"，所以 `<button v-hasPerm="[]">` 是空操作而不是隐藏。
3. **为什么藏按钮不等于拦截**：DOM 是客户端的东西。删掉按钮只是让人在界面上找不到入口，任何人用 curl 或改 JS 都能直接打接口。**权限必须由服务端在接口层回答**。
4. **两者为什么不会错位**：它们读同一份权限码——前端拿的是 `/auth/profile` 的 `permissions`（或 `/auth/routers` 派生的集合），后端用的是同一个 `current.perms`。

**③ 仓库证据**：`frontend/src/directives/hasPerm.ts`（注释第一句就是"it does **not** enforce anything"）、
`frontend/src/utils/permission.ts::hasPermission`、`frontend/src/directives/index.ts::setupDirectives`、
测试 `frontend/src/directives/__tests__/hasPerm.spec.ts`（7 项，含 `removes the element when the permission is missing`、`treats the wildcard as "everything"`）。

**④ 追问与短答**

- **Q：为什么不直接在按钮上加 `v-if`？** A：`v-if` 要在每个组件里重复写权限判断，而且判断逻辑会散落；指令 + 纯函数只写一次。
- **Q：指令只在 `mounted` 检查，权限变了怎么办？** A：P0 的权限在会话内不会变（改了角色要重新登录或刷新才会重新水合）。如果要做"权限热更新"，得加 `updated` 钩子或让 store 变更触发重渲染——这是我知道的缺口，没做。
- **Q：那前端藏按钮的意义是什么？** A：体验和误操作防护：不该点的人看不到入口，也不会有 403 弹窗。
- **Q：如果接口忘了加 `require_perm` 呢？** A：那这个接口就是全登录用户可访问。所以我在计划里把"每个写接口必须声明权限码"写成 Global Constraints，并在 P1 的 Review Focus 里要求逐条断言 403。

## 4. 令牌与会话

### 4.1 为什么令牌要落库，而不是纯无状态 JWT

**① 一句话答案**："纯无状态 JWT 无法撤销——'登出立刻失效''强制下线''在线用户'全都建立在一张按 `jti` 索引的服务端记录上。"

**② 30 秒结构化回答**

1. **代价**：每个已认证请求多一次按 `access_jti` + `revoked=0` 的索引查询（`ix_sys_user_token_access_jti`）。
2. **收益**：登出把那一行置 `revoked=True`，同一个令牌下一次请求就是 401；配对的 refresh 也一起失效。
3. **连带效果**：刷新时撤销的是**整行**，所以刷新之后**旧 access 令牌立即失效**——这是实测确认的行为，不是我从代码推的。
4. **再往上一层**：`get_current_user` 查完会话行还要单独查用户状态，所以"停用账号"和"逻辑删除账号"都会让已签发的令牌当场失效。

**③ 仓库证据**：`backend/app/models/token.py` 模块 docstring（原文写了"logging out actually means something"）、
`backend/app/core/deps.py::get_current_user`、`backend/app/services/auth_service.py::_issue_tokens`、`::refresh_tokens`、`::revoke_by_access_jti`；
测试 `tests/test_authz.py::test_logout_invalidates_the_token_immediately`、`::test_logout_also_ends_the_refresh_session`、`::test_disabling_an_account_invalidates_its_live_token`、`::test_deleting_an_account_invalidates_its_live_token`；
实测序列见 `docs/接口清单.md` §2.6 与 `docs/架构设计.md` §7.3。

**④ 追问与短答**

- **Q：那 JWT 还有什么意义？** A：它承载身份（`sub`、`jti`、`type`、`exp`），省掉了查会话表之前的一次解析失败路径；但"能不能用"由服务端记录说了算。这就是"令牌是声明，会话记录才是事实"。
- **Q：为什么不干脆用不透明随机串？** A：可以，那样更简单。我选 JWT 是因为它有 `type` 区分 access/refresh，而且 `exp` 能在解码层就拦掉明显过期的令牌。
- **Q：`sys_user_token` 只增不减的问题你怎么说？** A：**没修**，是已知遗留：每次登录和刷新都插一行，重复登录不撤销旧会话，也没有清理任务。表会持续增长，P1 的"在线用户"列表会因此变脏。建议在 P1 做在线用户时一并处理。
- **Q：为什么 `sys_user_token.user_id` 不建外键？** A：这张表是会话流水。挂外键会把"删用户"和"清会话"绑成数据库级联，而逻辑删除根本不触发级联；更糟的是未来的物理清理会静默销毁撤销记录。所以只留带索引的普通列，会话生死由应用决定。

### 4.2 登出到底撤销了什么

**① 一句话答案**："撤销的是**当前这一个会话**（整行），不是这个账号的所有会话。"

**② 30 秒结构化回答**

1. **凭什么定位到那一行**：`CurrentUser.access_jti` 保存了 `get_current_user` 里已经验签过的那个 `jti`，登出路由不需要再解一次令牌。
2. **为什么撤销整行**：这样"登出"意味着"这个会话结束了"，配对的 refresh 一起失效。
3. **为什么不是所有会话**："把该账号所有会话踢掉"是"强制下线"功能（P1，按 `token_id` 撤销），不该混进登出。
4. **幂等**：按 `access_jti` 找不到行时静默返回，重复登出不报错。

**③ 仓库证据**：`backend/app/services/auth_service.py::revoke_by_access_jti`、
`backend/app/api/v1/auth.py::logout`、`tests/test_authz.py::test_logout_marks_the_row_revoked`。

**④ 追问与短答**

- **Q：refresh 令牌单独泄露了怎么办？** A：它换不出新令牌——前提是那一行已经 `revoked`。如果泄露时用户还没登出，攻击者能刷新一次，之后合法客户端的下一次刷新会失败（旧 refresh 已被轮换撤销），这是一个**可见信号**。
- **Q：有 token 黑名单吗？** A：没有独立黑名单；`revoked` 列就是它。
- **Q：多个设备同时登录会互相踢吗？** A：不会。每次登录插新行，每个 `jti` 独立。
- **Q：登出后刷新页面会怎样？** A：前端 `localStorage` 令牌已被清（`removeTokens()`），守卫拦回 `/login?redirect=...`。浏览器验收记录了这一条。

### 4.3 刷新轮换 + 前端单飞：并发 401 只刷新一次

**① 一句话答案**："后端刷新即轮换（旧 refresh 立刻作废），前端的刷新是单飞的——三个并发 401 只触发一次刷新，**有测试钉住这件事**。"

**② 30 秒结构化回答**

1. **后端轮换**：`refresh_tokens` 解码 refresh → 按 `refresh_jti` + `revoked=0` 查行 → 校验过期与用户状态 → `record.revoked = True` → **同一个事务**里签发新的一对。
2. **为什么必须轮换**：轮换让重放可检测——被盗的 refresh 最多用一次，而且合法客户端的下一次刷新会失败。
3. **前端单飞**：`refreshPromise` 是模块级变量，`refreshAccessToken()` 里"没有在飞行中的就创建，有就 await 同一个"，`finally` 里清空。
4. **为什么单飞是必须的**：轮换三次会让其中两次拿到的令牌立即失效；`Promise.all` 里三个请求同时 401 是最常见的场景。

**③ 仓库证据**：
- 测试名（前端，`frontend/src/utils/__tests__/request.spec.ts`）：`refreshes once when three requests get 401 concurrently`——断言 `state.refreshCalls === 1` 且三次重放都带新令牌。
- 同一文件还有：`does not try to refresh a 401 from the refresh endpoint itself`、`gives up after one retry instead of looping`、`clears tokens and signals session expiry when the refresh itself fails`、`ends the session when the replay is rejected with the fresh token`、`keeps the session when the replay fails with a server error` / `...is forbidden` / `...at the network layer`。
- 后端：`tests/test_authz.py::test_refresh_rotates_and_rejects_the_old_refresh_token`、`::test_access_token_cannot_be_used_as_a_refresh_token`、`::test_refresh_token_cannot_be_used_as_an_access_token`。
- 代码：`frontend/src/utils/request.ts`（`refreshPromise`、`performRefresh`、两个 axios 实例）、`backend/app/services/auth_service.py::refresh_tokens`。

**④ 追问与短答**

- **Q：为什么用两个 axios 实例？** A：`service` 带拦截器，`refreshClient` 是裸的，所以"刷新接口自己 401 又去刷新"在**结构上**不可能，而不是靠一个可能被忘记检查的标志位。
- **Q：`_retried` 标志是干什么的？** A：标记"这次请求已经重放过"，所以最多重放一次，不会无限循环。
- **Q：刷新成功后重放失败（500/403/超时）会怎样？** A：**保留会话**，只提示错误。重放刻意放在刷新的 `try` 之外——否则重放遇到 500 会走"会话失效"分支清空令牌，把用户从一个完全有效的会话里踢出去。这是评审发现的一个 Important（见 §7.4）。
- **Q：多标签页同时刷新呢？** A：**会被踢**。轮换没有宽限期，两个标签页读到同一个旧 refresh 令牌时后者会失败。前端单飞只在同一个页面内生效，跨标签页不共享这个 Promise。这是我**接受的代价**，修法是"同一旧令牌短时间内复用视为合法"的宽限窗口——我把它列进了遗留清单，没有假装解决。
- **Q：为什么令牌存 `localStorage`？** A：见 §9.4，这是明确的已知短板。

## 5. 逻辑删除

### 5.1 全局 `do_orm_execute` 过滤器

**① 一句话答案**："`del_flag` 由一个导入即生效的全局 `do_orm_execute` 监听器统一过滤，业务代码**不写** `WHERE del_flag='0'`。"

**② 30 秒结构化回答**

1. **为什么是全局**：模块 docstring 的原话是——"只在调用点记得安装的过滤器，就是一个等待发生的数据泄漏"。`app/db/soft_delete.py` 最后一行 `install_soft_delete_filter()` 在导入时就挂上，任何会话的 ORM SELECT 都被过滤。
2. **怎么实现**：`with_loader_criteria(SoftDeleteMixin, lambda cls: cls.del_flag == DelFlagEnum.EXISTS, include_aliases=True)`；只作用于 SELECT，且跳过列加载与关系加载（复用父语句条件，重复施加会产生重复 WHERE）。
3. **按 mixin 匹配而不是按表名枚举**：带 `del_flag` 的自动覆盖（`sys_user`/`sys_role`/`sys_dept`/`sys_post`），不带的不受影响（`sys_menu`/`sys_user_token`/`sys_login_log`/四张关联表）。
4. **它不负责删除**：过滤器对 INSERT/UPDATE/DELETE 没有影响，"逻辑删除"是一个必须由业务代码执行的动作（把 `del_flag` 置 `'2'`），过滤器只负责让被删的行**读不到**。

**③ 仓库证据**：`backend/app/db/soft_delete.py`（`_soft_delete_listener`、`install_soft_delete_filter`、`include_deleted`）、
逃生口两种写法（会话级 `include_deleted(session)` / 语句级 `execution_options={"include_deleted": True}`）；
测试 `tests/test_models_migration.py::test_soft_delete_filter_is_installed_on_import`、`::test_install_soft_delete_filter_is_idempotent`、`::test_deleted_rows_are_hidden_from_queries`、`::test_include_deleted_reveals_hidden_rows`。

**④ 追问与短答**

- **Q：`install_soft_delete_filter(session)` 参数被忽略了，为什么不删？** A：因为它的语义是"确保全局监听器已挂载"的幂等保险，`get_db` 和测试 fixture 都显式调它来声明这个要求。留一个看起来多余的函数是刻意的，docstring 写明了原因。
- **Q：登录查询为什么又手写了一遍 `del_flag`？** A：`auth_service._find_user` 在全局过滤器已生效的前提下又写了一遍。理由是那次查询是**唯一**一个"过滤回归会直接发出去一个会话"的地方——别的查询顶多显示一条已删记录。
- **Q：全局过滤会不会误伤想查已删数据的管理页？** A：会，所以有显式逃生口。审计类查询要用时写明 `include_deleted`，而不是关掉全局过滤器。
- **Q：性能呢？** A：每个 SELECT 都会多一个 `del_flag = '0'` 条件，走的是各表已有的索引前缀，P0 数据量下没有可观测差异——我没有做过压测，这是判断不是测量。

### 5.2 为什么 `user_name` 故意不建唯一索引

**① 一句话答案**："因为逻辑删除后那行还在表里——`UNIQUE` 会让'删掉 zhangsan 再建一个 zhangsan'直接撞唯一键失败，而那条记录在业务上根本不该算存在。"

**② 30 秒结构化回答**

1. **语义冲突**：`del_flag='2'` 的行仍然占据 `user_name` 这个键。
2. **我的选择**：`user_name` / `role_key` / `post_code` 只建普通索引（`ix_sys_user_user_name` 等），**全库除了各个 `PRIMARY` 没有任何 `UNIQUE KEY`**。
3. **代价落在正确性上**：可能出现两条 `user_name` 相同、`del_flag` 同为 `'0'` 的活记录，而 `_find_user` 用 `db.scalar(...)` 会**静默取第一条**。
4. **配套**：唯一性必须由 service 层在事务内校验——**而这一层 P0 没有写**，P1 用户/角色 CRUD 落地前必须补。

**③ 仓库证据**：`backend/app/models/user.py`（`user_name` 上方注释 "Indexed but deliberately NOT unique"）、`backend/app/models/role.py`；
测试 `tests/test_models_migration.py::test_user_name_has_no_unique_index`（查 `information_schema.statistics` 的 `non_unique` 全为 1）、
`::test_deleted_user_name_can_be_reused`；
文档侧：`docs/数据库设计.md` §6.1（含"⚠ P0 的真实状态：这个 service 层校验**不存在**"）、`docs/P0决策记录.md` §四第 1 条。

**④ 追问与短答**

- **Q：那你怎么保证不出现同名活记录？** A：**P0 不保证**。因为 P0 没有任何创建接口，产生不了重复。这是一个"现在不构成缺陷、但会在 P1 变成缺陷"的缺口，我把它写成了 P1 的阻塞项。
- **Q：为什么不建"`(user_name, del_flag)` 联合唯一索引"这种折中？** A：那是我事后想到的更漂亮的做法，但它有个恶心的地方：同一条记录被删两次、或 `del_flag` 用更多状态值时会撞。而且它只能挡 `del_flag` 组合，挡不住"两条活记录"以外的其它语义。P1 我会先做 service 层校验，把约束放在业务层，因为报错信息要说人话。
- **Q：那这两条路哪个更好？** A：看你要什么：数据库唯一索引是**硬保证**，service 校验是**好报错**。我选了硬保证缺位、好报错待补，所以我在文档里把这一条标成了必须优先补的缺口，而不是"已解决"。
- **Q：删除后重建同名，登录会用哪一条？** A：只会用活的那条，因为已删的行被全局过滤器挡住，`_find_user` 又额外写了 `del_flag='0'`。测试是 `tests/test_auth.py::test_soft_deleted_account_cannot_log_in`。

### 5.3 对比：`sys_menu` 为什么**没有** `del_flag`

**① 一句话答案**："菜单被删就该真消失，否则它的 `perms` 会残留在所有曾持有它的角色权限集里——那是一个被撤销的权限点继续放行接口调用。"

**② 30 秒结构化回答**

1. **权限码的来源是菜单**：`get_current_user` 把启用菜单的 `perms` 收进权限集合。
2. **如果菜单也逻辑删除**：菜单不显示了，但 `perms` 仍留在角色权限集里——这是安全语义上的错，比"菜单没删干净"严重得多。
3. **所以删除是物理删除**：`sys_role_menu` 的外键是 `ON DELETE CASCADE`，P1 计划里仍会显式删掉关联行——级联能兜住，但显式删除看得出意图。
4. **代价**：删菜单不可逆——而这恰好是种子/重置流程想要的语义。

**③ 仓库证据**：`backend/app/models/menu.py` 类 docstring（"Deliberately has no `del_flag`"）、
`docs/数据库设计.md` §6.2、`docs/P0决策记录.md` §二。

**④ 追问与短答**

- **Q：那误删菜单怎么办？** A：重新跑 `python -m scripts.seed_data`——种子脚本对菜单用 `_upsert_presentation`，**已存在的行会刷新展示字段**，所以常量就是事实来源。用户和角色则用 `_get_or_create`，已存在就完全不碰（注释写着 "Never silently reset a password on a re-run; say so instead"）。
- **Q：种子脚本会不会覆盖别人手工改的菜单标题？** A：会，而且这是**意图**：改了图标或标题再跑一次种子应该生效。它只覆盖 `MENU_MUTABLE_FIELDS` 里的 13 个展示字段，绝不覆盖密码或状态。
- **Q：这两个相反的决定（业务表逻辑删除、菜单物理删除）怎么自洽？** A：判据是"这行数据还携带权限语义吗"。用户/角色/部门/岗位删掉之后不应该再出现在任何查询里，但它们的历史必须留；菜单一旦不该存在，它的权限码就必须消失。

### 6.1 先钉住口径

### 6.2 它将怎么实现（P1-A 计划里的设计）

**① 一句话答案**："在**查询构造期**注入 `WHERE`，不是在查完之后过滤；'本部门及以下'用 MySQL 8 的递归 CTE 在库内求子树；多角色取**最宽松**。"

**② 30 秒结构化回答**

1. **入口唯一**：`app/services/data_scope.py` 提供 `resolve_data_scope(roles, *, user_id, dept_id, is_admin) -> DataScope` 与 `apply_data_scope(stmt, entity, scope, *, dept_field="dept_id", user_field="user_id")`；每个受控列表把语句包一层，**业务代码里不出现任何 `if is_admin` 分支**。
2. **五种模式的 SQL**：`ALL` 原样返回；`DEPT` → `dept_id = :current_dept_id`；`DEPT_AND_CHILD` → `dept_id IN (递归 CTE 子树)`；`CUSTOM` → `dept_id IN (sys_role_dept 里该角色的部门)`；`SELF` → `user_id = :current_user_id`。
3. **递归 CTE**：锚点 `dept_id = :root`，递归项 `JOIN dept_tree t ON d.parent_id = t.dept_id`；软删除由全局过滤器自动生效，**不手写 `del_flag`**。
4. **最宽松胜出**：多角色取 `mode` **数值最小**者（1 最宽松），`CUSTOM` 的部门集合取并集；这一点必须写进 docstring，否则后人会以为数值越大越宽松。

**③ 仓库证据**：`docs/superpowers/plans/2026-10-17-p1a-data-scope-and-rbac-crud.md` Task 1（接口签名与测试名清单）、Task 7（接进列表接口 + 补 HTTP 层分页边界）；
设计文档 §6.4 的递归 CTE SQL；`backend/app/utils/tree.py::build_tree` 已经存在，部门树可直接复用。

**④ 追问与短答**

- **Q：为什么不在 `api/` 层过滤？** A：那会让每个接口各自实现一遍范围判断，漏一个就是越权。放在 service 的查询构造处，Review Focus 第一条就是"越权可见"——P1 计划里它是**最严重**的失败模式。
- **Q：`DEPT_AND_CHILD` 用 `ancestors LIKE '0,1%'` 不是更快吗？** A：`sys_dept.ancestors` 的物化路径确实能让"X 是否 Y 的后代"用 LIKE 回答，模型注释里也写了这个用途。但 LIKE 在数据权限里容易出前缀误判（`0,1` 会匹配 `0,10`），所以计划里"热路径判断用 LIKE、数据权限用递归 CTE"是两个用途分开的。
- **Q：多角色"最宽松"会不会导致越权？** A：这是**有意的策略**：用户被授予两个角色时按并集看待权限。如果业务上要"最严格"，那是另一个产品决策——我选择并集，并且会把它写进菜单授权页的说明里。
- **Q：`data_scope` 存成 `varchar(1)` 而枚举是 `IntEnum`，不别扭吗？** A：别扭。模型里用了 `default=str(int(DataScopeEnum.ALL))` 把 `1` 变成 `"1"`。理由是跟 `status`/`del_flag` 这些字符串状态列保持一致，也让 DBA 直接看库时一眼能懂。我承认这不是最干净的做法。
- **Q：P1 你准备怎么证明它真的生效？** A：三条用同一份数据、只换登录角色的断言：`test_user_list_respects_dept_scope`、`test_user_list_admin_sees_everything`、`test_user_list_self_scope_sees_only_self`——**断言的是行数不同**，这正是成功标准 S2 那句话。

### 7.4 讲一个具体 bug（这是最能得分的一段）

**先主动交代**："P0 完成后，由一个**全新上下文的评审者**只读评审整支分支，结论是**无 Critical、4 个 Important、8 个 Minor**。
4 个 Important 我全部接受并修掉了，每条都是**先写出失败测试再改代码**。其中两个是我自己完全没覆盖、评审用独立探针复现的。"

#### 故事 A（主讲）：重放遇到非 401 失败，把用户从一个有效会话里踢出去

1. **现象**：刷新令牌成功后要重放原请求。原来的实现把重放包在刷新那个 `try` 里——重放返回 500/403/超时，全都落到"会话已失效"分支：清空令牌、硬跳登录页。
2. **为什么是真问题**：后端重启造成一次瞬时 500，用户就被登出了，而手里的 refresh 令牌还是完全有效的。这是"把意外当成了身份判定"。
3. **修法（测试先行）**：只让**刷新失败**或**重放再次 401**结束会话；重放放在 `try` **之外**（`frontend/src/utils/request.ts` 第 144–149 行有注释写明理由）。先补 3 条失败测试再改代码：`keeps the session when the replay fails with a server error`、`...is forbidden`、`...at the network layer`。
4. **最尴尬的细节（我会主动说）**：我自己的测试辅助函数 `rotatingResponder({ secondStatus })` 当初**就是为这个场景写的**，却从来没被使用——评审者指出这一点。教训是：写了一个测试工具却没写用例，等于承认那条路径没被验证。
5. **一句话总结**："401 说'身份无效'，500 只说'这次没成功'；把两者当一回事，就是用偶发故障奖励了一个登出。"

#### 故事 B（主讲）：零角色账号永远进不了页面

1. **现象**：导航守卫用"有没有角色"当作"是否已水合"的哨兵。零角色账号的 `roles` 合法地是 `[]`，于是守卫反复水合并重放同一次导航。
2. **为什么是真问题**：评审者实测**一次导航触发 32 次 profile 请求**，生产构建下是无限循环。这不是性能问题，是功能不可用——而且它伤的正是我专门做出来演示"零权限不白屏"的那类账号。
3. **修法**：用户 store 增加独立的布尔标记 `hydrated`（`frontend/src/stores/user.ts`），守卫只看它。先补 `frontend/src/router/__tests__/guard.spec.ts` 的 4 条，其中第一条就是 `reaches the page for an account with no roles, hydrating exactly once`，断言 `getProfile` 只被调用 1 次。
4. **一句话总结**："空数组是一个合法值，不是'还没加载'。用一个空值当哨兵，等于让合法的空状态永远看起来像未初始化。"

#### 故事 C（备用）：5 次锁定能被大小写绕过

1. **现象**：MySQL 的 `utf8mb4_0900_ai_ci` 排序规则大小写不敏感，`ADMIN` 命中 `admin` 那一行；但失败计数器的 key 用的是**原始输入串**，于是每种拼写各给 5 次机会。
2. **为什么是真问题**：README 承诺的"5 次锁定"实际上等于无限次；而且带空格、混合大小写都能重置预算。
3. **修法**：`_lockout_key()` 做 `strip().casefold()` 归一（`backend/app/services/auth_service.py`）；新建 `tests/test_lockout.py` 5 条：大写、混合、空白、反向、两个账号预算互不影响。
4. **一句话总结**："凡是拿用户输入当 key 的地方，都要先问一句'数据库比较这个字段时是怎么比的'。"

#### 故事 D（备用）：停用/已删角色仍在通过 `/auth/routers` 下发菜单

1. **现象**：接口层和 profile 层都忽略停用角色，唯独菜单层没 join `sys_role`。
2. **为什么是真问题**：同一个账号在不同层得到**互相矛盾**的答案——profile 说没有角色，侧边栏却列着菜单，而每个按钮都 403。两套答案里总有一套是错的，用户无法判断。
3. **修法**：查询补 join 并按 `status` 过滤（`sys_role` 自带逻辑删除过滤，已删角色自动排除）；新增 3 条测试，除两条负例外还加了 `test_routers_still_return_menus_for_a_normal_role` 防"修过头"。

**追问与短答**

- **Q：这 4 个 bug 都是你自己发现的吗？** A：**不是**。都是独立评审发现的。我自己测出来的问题（比如 `git add` 漏文件）在 §8.3。这一点我主动说，因为它决定了我对自己测试套件的信任程度：**它证明了我覆盖过的路径，证明不了我没覆盖的路径**。
- **Q：为什么评审者能找到，你找不到？** A：因为我自己写测试时会顺着实现的思路走；评审者从"用户会怎么失败"出发。所以 P0 之后我加了一条流程：验收记录里专门写一节"本次验收未覆盖的范围"。
- **Q：还有一个 Important 是哪个？** A：就是故事 C 和 D，加上 A、B 一共 4 个。Minor 评审结论里记了 8 条，我把它们和评审对文档的核实意见一起展开成 11 条，全部列在 `docs/P0决策记录.md` §四 —— 一条都没修，但每条都写清了影响和建议时机（例如 `sys_user_token` 只增不减、`DEBUG` 默认 `true`、`PageParams` 是死代码、多标签页刷新互踢）。

### 7.5 测试基础设施（被问"怎么搭的"时用）

**① 一句话答案**："独立测试库 + 每用例一个事务回滚 + `httpx.ASGITransport` 直连应用，不起真实服务。"

**② 30 秒结构化回答**

1. **`conftest.py` 的三个关键 fixture**：`db_session`（外层事务 + `join_transaction_mode="create_savepoint"`，用例里可以自由 `commit()` 也逃不出回滚）、`client`（覆写 `get_db` 依赖，让请求共享同一个会话）、`migrated_test_database`（session 级，编程式跑一次 `alembic upgrade head`）。
2. **为什么 `NullPool`**：pytest-asyncio 每个用例一个事件循环，池化连接不能跨循环复用。
3. **为什么 `raise_app_exceptions=False`**：真实服务器会先渲染 500 响应再重抛；测试客户端必须看到同样的东西，否则"未捕获异常"的用例永远观察不到处理器的输出。
4. **一次全局缓存清理**：`cache` 是模块级单例，`_isolated_cache` 在每个用例前后清空，否则上一个用例的锁定计数会污染下一个。

**③ 仓库证据**：`backend/tests/conftest.py`（含 `_make_user`/`_grant_role`/`_grant_menu` 与 `menu_tree`、`permitted_user` 等域 fixture）、
`backend/pytest.ini`（`asyncio_mode = auto`、`pythonpath = .`、`asyncio_default_fixture_loop_scope = function`）。

**④ 追问与短答**

- **Q：`asyncio_mode = auto`，测试不用装饰器？** A：对，`async def test_*` 直接就是异步用例。
- **Q：为什么授权测试单独一个文件？** A：认证（你是谁）和授权（你能做什么）是两个关注点，混在一起改一个要通读另一个。计划里本来要求追加进 `test_auth.py`，我拆成了 `test_authz.py`。
- **Q：为什么 `_grant_role` 不直接 `user.roles.append(...)`？** A：已 flush 的实例上这个集合从未被查询加载过，碰它会触发懒加载——异步下抛 `MissingGreenlet`。直接写关联行更诚实，也说清了发生了什么。

## 8. 工程习惯

### 8.1 流程：spec → plan → TDD → 独立评审 → 修复轮

**① 一句话答案**："我先写设计文档，再把它拆成 17 个任务的实施计划，每个任务都是'先写失败测试 → 跑出失败 → 实现 → 跑绿 → 提交'，

**② 30 秒结构化回答**

1. **spec**：`docs/superpowers/specs/2026-10-17-enterprise-admin-design.md`（架构、数据模型、四层权限、接口规范、分期计划、风险）。
2. **plan**：`docs/superpowers/plans/2026-10-17-p0-foundation-and-login.md`，17 个任务，每个任务有 Files / Interfaces / Step，**每步都是单一动作**（写测试 → 看失败 → 实现 → 看通过 → 手动验证 → 提交），计划末尾还有"计划自查"逐条核对 spec 覆盖。

### 8.3 一次真实的失败：HEAD 跑不过自己的测试

**① 一句话答案**："Task 10 提交时，一处 `CAPTCHA_ENABLED` 门控漏进了 `git add` 清单——**工作区测试全绿，HEAD 上 4 条测试有 2 条失败**。"

**② 30 秒结构化回答**

1. **现象**：我在工作区里跑测试是全绿的，但那一次提交并不包含全部改动。用 `git stash` 隔离工作区改动之后，HEAD 才暴露出 4 条测试里 2 条失败。
2. **根因**：提交时按文件路径 `git add`（计划的每个任务都列了 `git add` 清单），漏了一个文件。这是我"按清单提交"这个习惯的副作用——清单是手写的。
3. **修法**：补一个独立提交 `c16e244 fix(backend): commit the CAPTCHA_ENABLED gate omitted from the Task 10 commit`；更重要的是改了流程：**每次验收的第一步是确认工作区干净**，并且验收对象是 **HEAD**，不是工作区。
4. **教训**：绿色的是工作区，不是提交。"我本地是好的"这句话在有版本控制的项目里不是证据。

**③ 仓库证据**：`docs/P0验收记录.md` 开头那段引用（"为什么强调「干净工作区」"）、`git log` 里的 `c16e244`。

**④ 追问与短答**

- **Q：为什么不用 `git add -A`？** A：计划里逐个文件列 `git add` 是为了让每个提交自洽、避免误提交；代价就是漏文件。事后看，`git add -A` + 提交前 `git status` 复核更安全。
- **Q：这件事之后你改了什么？** A：验收记录的第一节从"跑测试"变成"先确认工作区干净"，而且明确写"在 HEAD 上执行"。P1-A 计划的 Global Constraints 里也复述了这条。
- **Q：还有别的流程性失误吗？** A：有，都在决策记录里：调用原生 exe 时把 `$ErrorActionPreference` 从 `Stop` 放宽成 `Continue`（因为 git 往 stderr 写正常输出会被当成终止性错误），代价是非预期 cmdlet 失败不会中断脚本——这是一笔我自己认下的债。
- **Q：你从整个 P0 学到的最大一条是什么？** A：**把"已验证的范围"和"我推断的范围"分开写**。前者能写进验收记录，后者只能写进"未覆盖"那一节。

## 10. 高频追问清单（28 题，按主题分组）

> 每题答案控制在 1–3 句。带 ⚠ 的是"必须承认"的题。

### A. 项目与自我介绍

1. **一句话说清这个项目是什么？** → 企业后台管理系统的底座/作品集项目，用"登录 + 权限"一条垂直切片证明我能把 RBAC、动态路由、可撤销会话讲清楚并跑起来。
2. **为什么要做这个项目？** → 我 8 年前端、主栈 Vue 2，要投全栈岗需要一个能现场演示、代码结构经得住追问的东西；我没做一堆 CRUD，而是先把骨架和权限闭环做扎实。
3. **你在这个项目里最想展示什么？** → 两个取舍：令牌落库换"登出即刻失效"；为逻辑删除故意不建唯一索引、把唯一性交给 service 层（并且诚实标注这层还没写）。

### B. 权限与安全

4. **四层权限都实现了吗？** ⚠ → 接口级、菜单/路由级、按钮级已实现；**数据级是 P1**，只有表结构。
5. **隐藏按钮算权限控制吗？** → 不算。DOM 是客户端的，删掉按钮只是体验优化；真正的拦截在服务端接口层的 `require_perm`。
6. **前端藏了按钮，后端没拦，会怎样？** → 我直接 curl 就能调用。所以我把"每个写接口必须声明权限码"写进了计划约束，两者读同一份权限码（`/auth/profile` 的 `permissions` 与 `current.perms`）所以不会错位。
7. **超管为什么绕过权限码比对？** → 角色 key 是 `admin` 就直接放行（`perms` 给 `*:*:*`），避免新增功能后管理员被自己的权限系统锁死。
8. **401 和 403 的区别你怎么设计的？** → 401 是"身份问题"（无令牌/过期/撤销/账号停用或删除，**共用同一条消息**）；403 是"身份没问题但权限不够"，用 `logger.info` 记下被拒的权限码。
9. **为什么验证码错误不计入锁定？** → 否则任何人只要知道用户名就能把账号锁死。所以顺序固定为**验证码 → 锁定 → 凭据**（`auth_service.authenticate` docstring）。
10. **被逻辑删除的账号登录会得到什么提示？** → 与"密码错误"完全相同（"用户名或密码错误"），因为说"账号已删除"等于告诉调用方哪些账号存在。
11. **`X-Forwarded-For` 你信吗？** → 只作为审计元数据，**绝不作为授权输入**；取第一跳，取不到再退 `X-Real-IP`、最后 `request.client.host`。
12. **500 会不会漏出堆栈或连接串？** → 不会。`_handle_unexpected` 把完整异常写日志并带 `request_id`，响应体只有一句通用提示；`loguru` 的 `diagnose` 也关掉了（否则局部变量值会进 traceback）。我还在真实进程上停掉 MySQL 验证过一次。

### C. 令牌与会话

13. **JWT 为什么要落库？** → 无状态令牌没法撤销；落库后按 `access_jti` + `revoked=0` 查一行，登出/强退/在线用户才成立，代价是每个请求多一次索引查询。
14. **登出到底撤销了什么？** → 当前这一个会话的整行（`revoke_by_access_jti`），所以配对的 refresh 也失效；结束该账号全部会话是 P1 的"强制下线"。
15. **刷新为什么要轮换？** → 让重放可检测：旧记录在同一事务里被撤销，被盗的 refresh 最多用一次，而且合法客户端的下一次刷新会失败（可见信号）。
16. **三个请求同时 401 会刷新几次？** → **一次**。前端 `refreshPromise` 单飞，测试 `refreshes once when three requests get 401 concurrently` 断言 refresh 调用次数恰为 1、三次重放都带新令牌。
17. **多标签页同时刷新呢？** ⚠ → **会被踢**。轮换没有宽限期，前端单飞只在同一页面内生效。这是我接受的代价，修法是加"旧令牌短时间复用视为合法"的宽限窗口，已列入遗留清单。
18. **为什么用两个 axios 实例？** → 让"刷新接口自己 401 又去刷新"在结构上不可能，而不是靠一个可能忘记检查的标志位。

### D. 数据库与 ORM

19. **为什么 `user_name` 不建唯一索引？** ⚠ → 逻辑删除后同名重建会撞唯一键；代价是唯一性得靠 service 层校验，而**这一层 P0 还没写**，是 P1 用户 CRUD 的阻塞项。
20. **全局逻辑删除过滤器怎么实现的？** → `app/db/soft_delete.py` 导入即给 `Session` 的 `do_orm_execute` 挂监听器，用 `with_loader_criteria(SoftDeleteMixin, del_flag='0', include_aliases=True)`；想查已删数据用 `include_deleted()` 显式逃生。
21. **`sys_menu` 为什么没有 `del_flag`？** → 菜单删了就该真消失，否则它的 `perms` 会残留在所有曾持有它的角色权限集里——等于一个被撤销的权限点继续放行接口。
22. **异步 ORM 你踩了什么坑？** → 隐式懒加载抛 `MissingGreenlet`；所以 `SysUser.dept` 用 `lazy="joined"`、`roles/posts` 用 `lazy="selectin"`，而且不声明反向关系（反向关系会让角色列表把该角色所有用户拖出来）。
23. **`update_time` 会自动更新吗？** → 只有走 ORM 的更新才会（`onupdate=func.now()` 是 ORM 层行为）；落库 DDL 里**没有** `ON UPDATE CURRENT_TIMESTAMP`，所以原始 SQL 改数据不会刷新它。
24. **时区怎么处理的？** → 应用写 naive UTC，库端 `default-time-zone='+00:00'`；两边不一致会让同一行里 `create_time` 与 `access_expire` 处在不同时区，几个月后以"过期令牌仍然有效"的形式爆出来。

### E. 前端工程

25. **Vue 3 你熟吗？** ⚠ → 会用、能改，但**不算深**：组合式 API、Pinia、`vue-router` 的动态路由我都能写；不如 Vue 2 熟的是响应式原理细节与生态里的新工具链。
26. **动态路由最容易踩的坑是什么？** → 两个：catch-all 必须在动态路由**之后**注册；注册完必须**重放导航**，否则 vue-router 已经判定目标未知、渲染 404。还有第三个：动态路由要挂在 Layout 的**子路由**下，挂根层级会让页面渲染在布局之外。
27. **零权限账号会白屏吗？** → 不会。`/auth/routers` 返回 `[]` 是 200 不是错误，前端生成空路由、侧边栏显示"当前账号没有任何菜单权限"。这也是我保留 `staff`/`nobody` 两个演示账号的原因。
28. **守卫怎么判断"已经水合过"？** → 用独立的 `hydrated` 布尔标记，**不用**"roles 非空"——零角色账号合法地有 `roles: []`，用它当哨兵会导致无限重定向（评审实测一次导航 32 次 profile 请求）。

### F. 测试与工程习惯

29. **测试多少？覆盖了什么？** → 后端 130、前端 40；覆盖认证链路、授权判定、令牌生命周期、逻辑删除、缓存并发、菜单树、异常与响应、以及前端请求层/store/指令/守卫。

- 验收 → 在 HEAD 与干净工作区上做过，浏览器场景有截图，**未覆盖范围单独列了一节**。

**三个数字要一次报对**：后端 **130**（10 个文件）、前端 **40**（5 个文件）、接口 **7** 条（6 条 `/api/v1` + `/health`）。

**三个最容易讲错的细节**：
1. `manager` 只看到 4 项菜单 —— 那是**菜单级**权限，不是数据权限。
2. 隐藏菜单**仍会下发**（`sys_menu.visible` 不过滤，只翻译成 `hidden`）。
3. 刷新之后**旧 access 令牌立即失效**（撤销的是整行，不是单个 jti）。
