## P1-A 任务 1：数据权限机制

### 裁定

- **P1-A-1：多角色按并集实现，而非计划写的「取 `mode` 最小者胜出」。**
  计划（`docs/superpowers/plans/2026-10-17-p1a-data-scope-and-rbac-crud.md` 的 Task 1 接口）写的是「`mode` 最小者胜出」，
  但设计文档 §6.4 的原文是「用户有多个角色时取**并集**（权限最大化）」。两者**不等价**：
  一个「本部门」角色 + 一个「自定义两个部门」角色，取最小 `mode` 会选中 CUSTOM 而**丢掉用户自己的
  部门** —— 用户的可见范围反而变小了，与「权限最大化」相反。因此 `DataScope` 承载一组规则、
  构造查询时 `or_` 起来。设计文档是权威，计划只是它的论证。
  **代价（若判断有误）**：一个接口可能需要最多 3 个 OR 条件而不是 1 个；「本部门及以下」还会多一次
  子树查询。已用测试固定：`test_roles_union_rather_than_pick_one`、
  `test_a_narrower_role_does_not_narrow_a_broader_one`。

- **P1-A-2：`apply_data_scope` 的第一个参数是 `db`，与计划的签名不同。**
  计划的签名是 `apply_data_scope(stmt, entity, scope, ...)`，但「本部门及以下」必须查库算子树 ——
  原签名**根本无法实现该模式**。改为 `apply_data_scope(db, stmt, entity, scope, ...)`。
  **代价（若判断有误）**：每个受控列表多一次廉价的递归 CTE（每请求一次，不是每行一次）。

- **P1-A-3：没有规则的账号**失败关闭**。**
  `DataScope.rules` 为空时 `apply_data_scope` 追加 `WHERE false`。反过来的选择（不过滤）会让一个
  角色被全部停用的账号看到**全库数据** —— 那是数据权限里唯一真正致命的失败方向。
  已用测试固定：`test_a_scope_with_no_rules_sees_nothing`、
  `test_scope_grants_nothing_for_a_user_without_roles`。

- **P1-A-4：停用/已删角色不产生任何规则。**
  与 P0 评审修复的菜单层裁定保持一致（被撤销的角色什么都不给），避免出现「菜单看不到但数据能看到」
  这种更隐蔽的不一致。`test_disabled_roles_are_ignored`。

- **P1-A-5：`resolve_data_scope` 保持纯函数（不查库），子树查询留在 `apply_data_scope` 里。**
  这样可见范围的**判定逻辑**可以完全脱离数据库被测试（`resolve_data_scope` 的 10 条测试都不需要
  DB），而只有需要子树的那个模式需要连接。
  **代价（若判断有误）**：两种模式各自查一次库，而不是把子树预算一次性解析进 `DataScope`。

- **P1-A-6：新增 DEBUG 专用的 `GET /__test__/scope` 路由。**
  设计文档的 profile 响应只含 `{user, roles, permissions}`，**不含数据范围**（这是有意的：数据范围是
  服务端查询关注点，不是客户端状态）。因此「解析出来的范围真的挂到了当前用户上」这件事**无法**通过
  既有接口观察。加一个 DEBUG 门控的路由，让接线可以被真实 HTTP 断言证明，而不是靠读代码相信。
  **代价（若判断有误）**：多一个仅 DEBUG 存在的路由（已与既有 `/__test__/*` 同等待遇，
  `DEBUG=false` 时不注册）。

### 实施中发现的自身缺陷（已修）

- 调试路由 `_scope` 最初**直接返回裸 dict、没有套统一信封**，与其它所有接口的约定不一致，
  导致测试读到 `KeyError: 'data'`。已改为 `success(...)`。
- 数据范围字段一度**只被定义、没有被填充**：`CurrentUser.data_scope` 有默认值，所以
  `get_current_user` 不填它时，155 项测试**全部通过**，而每个真实请求拿到的是「看不到任何数据」。
  这是本次最危险的一类状态 —— 静默失效且测试全绿。是那三条**端到端接线测试**把它逼出来的
  （先看到 `unrestricted is False` 的失败，再修 `get_current_user` 的返回值）。

### 已验证

- 后端 `pytest`：**155 项通过**（P0 的 130 项全未受影响 + 本任务新增 25 项）
- `test_data_scope.py` 覆盖：五种模式的判定与查询效果、递归子树（含已删分支切断）、
  多角色并集、失败关闭、管理员不受限、以及三条真实 HTTP 接线断言
- 尚未接入任何列表接口 —— 那是任务 7 的事。目前**没有任何接口消费** `apply_data_scope`，
  这一点必须在文档里说清，不能让人以为数据权限已经生效。

## P1-A 任务 2：部门 CRUD

### 裁定

- **P1-A-7：部门列表**不**受数据权限过滤。**
  计划里列了一条 `test_dept_list_is_filtered_by_data_scope`，我判断它是**过度设计**：部门是组织树，
  按行级数据范围过滤会让树形 UI 只显示零散节点、无法表达层级；而数据权限真正要解决的问题是
  「同一张业务表里哪些**行**可见」，那属于用户等业务数据。这与业界参照实现一致（RuoYi 的部门列表
  也不做数据范围过滤）。**代价（若判断有误）**：一个「只应看到本部门」的角色仍能看到完整组织树 ——
  组织架构本身通常不算敏感数据，但如果这一假设不成立，需要改成「按子树裁剪」而不是「按行过滤」。

- **P1-A-8：部门列表**不分页**，但仍使用统一的分页信封。**
  一棵树被从中间截断就不再是树，所以 `page_size` 在这个接口上没有意义；响应仍返回
  `{rows, total}`，避免前端为这一个接口写特例。任务 7 的接口层分页边界测试会打在一个**真正分页**的
  接口（用户列表）上，而不是这里。**代价（若判断有误）**：部门数量极大时该接口会一次返回全量。

- **P1-A-9：同名校验是**同级**范围内的，且由 service 层在事务内完成。**
  两个不同父节点下可以各有一个「研发部」（现实中的组织就是这么命名的）；不建数据库唯一索引是因为
  逻辑删除后必须允许重建同名。这正是 P0 评审留下的「承诺了但不存在」的那条校验，本任务开始逐模块补上。
  **代价（若判断有误）**：并发创建同名同级部门时仍可能双双成功（无唯一索引兜底）—— 见下方遗留。

- **P1-A-10：删除守卫返回 400 且带**可区分**的文案。**
  「存在下级部门」与「部门下存在用户」是两种不同的用户动作，都返回同一句泛化错误会让人无从下手。
  **代价（若判断有误）**：错误文案成为事实上的契约，前端若要按文案分支就会很脆 —— 所以前端应依据
  状态码 + 是否展示 msg，而不是匹配文案。

- **P1-A-11：补齐了种子里缺失的按钮权限码（`system:dept:*`、`system:post:*`、`system:role:query`）。**
  原本种子里只有用户/角色/菜单有按钮码，部门与岗位只有列表码。不补的话，**任何非管理员角色都不可能
  被授予部门/岗位的新增、修改、删除** —— 权限模型会是残缺的，而且这种残缺不会报错，只会表现为
  「怎么授都授不出这个权限」。已重新播种并查库确认 33 条菜单、11 个新码就位。
  **代价（若判断有误）**：种子数据文件变大；重新播种会刷新这些行（这是既定的种子语义）。

### 实施中发现的自身缺陷（已修）

- 编辑 `seed_data.py` 时一次误操作**去掉了 `system_role` 那行末尾的换行**，把两个元组接到同一行。
  语法仍然合法，所以不会有任何测试或类型检查报错 —— 属于「静默变丑且丢了一条按钮」的那类问题。
  发现方式是紧接着的 `read` 复查。教训：用 `old_string` 做替换时，**不要在同一段字符串里同时改动
  内容和结构**，一次只做一件事。
- 路由 `router.py` 的编辑一开始被文件策略拒绝，导致 19 条测试全部 404。这一步的教训是：
  「代码写完」与「代码被挂载」是两件事，测试红了要先分清是哪一种。
