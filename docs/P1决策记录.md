## P1-A 任务 1：数据权限机制

### 裁定

- **P1-A-1：多角色按并集实现，而非计划写的「取 `mode` 最小者胜出」。**
  计划（`docs/superpowers/plans/2026-10-17-p1a-data-scope-and-rbac-crud.md` 的 Task 1 接口）写的是「`mode` 最小者胜出」，
  但设计文档 §6.4 的原文是「用户有多个角色时取**并集**（权限最大化）」。两者**不等价**：
  一个「本部门」角色 + 一个「自定义两个部门」角色，取最小 `mode` 会选中 CUSTOM 而**丢掉用户自己的
  部门** —— 用户的可见范围反而变小了，与「权限最大化」相反。因此 `DataScope` 承载一组规则、
  构造查询时 `or_` 起来。设计文档是权威，计划只是它的论证。
  **代价（若判断有误）**：一个接口可能需要最多 3 个 OR 条件而不是 1 个；「本部门及以下」还会多一次
  子树查询。已用测试固定：`test_roles_union_rather_than_pick_one`、
  `test_a_narrower_role_does_not_narrow_a_broader_one`。

- **P1-A-2：`apply_data_scope` 的第一个参数是 `db`，与计划的签名不同。**
  计划的签名是 `apply_data_scope(stmt, entity, scope, ...)`，但「本部门及以下」必须查库算子树 ——
  原签名**根本无法实现该模式**。改为 `apply_data_scope(db, stmt, entity, scope, ...)`。
  **代价（若判断有误）**：每个受控列表多一次廉价的递归 CTE（每请求一次，不是每行一次）。

- **P1-A-3：没有规则的账号**失败关闭**。**
  `DataScope.rules` 为空时 `apply_data_scope` 追加 `WHERE false`。反过来的选择（不过滤）会让一个
  角色被全部停用的账号看到**全库数据** —— 那是数据权限里唯一真正致命的失败方向。
  已用测试固定：`test_a_scope_with_no_rules_sees_nothing`、
  `test_scope_grants_nothing_for_a_user_without_roles`。

- **P1-A-4：停用/已删角色不产生任何规则。**
  与 P0 评审修复的菜单层裁定保持一致（被撤销的角色什么都不给），避免出现「菜单看不到但数据能看到」
  这种更隐蔽的不一致。`test_disabled_roles_are_ignored`。

- **P1-A-5：`resolve_data_scope` 保持纯函数（不查库），子树查询留在 `apply_data_scope` 里。**
  这样可见范围的**判定逻辑**可以完全脱离数据库被测试（`resolve_data_scope` 的 10 条测试都不需要
  DB），而只有需要子树的那个模式需要连接。
  **代价（若判断有误）**：两种模式各自查一次库，而不是把子树预算一次性解析进 `DataScope`。

- **P1-A-6：新增 DEBUG 专用的 `GET /__test__/scope` 路由。**
  设计文档的 profile 响应只含 `{user, roles, permissions}`，**不含数据范围**（这是有意的：数据范围是
  服务端查询关注点，不是客户端状态）。因此「解析出来的范围真的挂到了当前用户上」这件事**无法**通过
  既有接口观察。加一个 DEBUG 门控的路由，让接线可以被真实 HTTP 断言证明，而不是靠读代码相信。
  **代价（若判断有误）**：多一个仅 DEBUG 存在的路由（已与既有 `/__test__/*` 同等待遇，
  `DEBUG=false` 时不注册）。

### 实施中发现的自身缺陷（已修）

- 调试路由 `_scope` 最初**直接返回裸 dict、没有套统一信封**，与其它所有接口的约定不一致，
  导致测试读到 `KeyError: 'data'`。已改为 `success(...)`。
- 数据范围字段一度**只被定义、没有被填充**：`CurrentUser.data_scope` 有默认值，所以
  `get_current_user` 不填它时，155 项测试**全部通过**，而每个真实请求拿到的是「看不到任何数据」。
  这是本次最危险的一类状态 —— 静默失效且测试全绿。是那三条**端到端接线测试**把它逼出来的
  （先看到 `unrestricted is False` 的失败，再修 `get_current_user` 的返回值）。

### 已验证

- 后端 `pytest`：**155 项通过**（P0 的 130 项全未受影响 + 本任务新增 25 项）
- `test_data_scope.py` 覆盖：五种模式的判定与查询效果、递归子树（含已删分支切断）、
  多角色并集、失败关闭、管理员不受限、以及三条真实 HTTP 接线断言
- 尚未接入任何列表接口 —— 那是任务 7 的事。目前**没有任何接口消费** `apply_data_scope`，
  这一点必须在文档里说清，不能让人以为数据权限已经生效。

## P1-A 任务 2：部门 CRUD

### 裁定

- **P1-A-7：部门列表**不**受数据权限过滤。**
  计划里列了一条 `test_dept_list_is_filtered_by_data_scope`，我判断它是**过度设计**：部门是组织树，
  按行级数据范围过滤会让树形 UI 只显示零散节点、无法表达层级；而数据权限真正要解决的问题是
  「同一张业务表里哪些**行**可见」，那属于用户等业务数据。这与业界参照实现一致（RuoYi 的部门列表
  也不做数据范围过滤）。**代价（若判断有误）**：一个「只应看到本部门」的角色仍能看到完整组织树 ——
  组织架构本身通常不算敏感数据，但如果这一假设不成立，需要改成「按子树裁剪」而不是「按行过滤」。

- **P1-A-8：部门列表**不分页**，但仍使用统一的分页信封。**
  一棵树被从中间截断就不再是树，所以 `page_size` 在这个接口上没有意义；响应仍返回
  `{rows, total}`，避免前端为这一个接口写特例。任务 7 的接口层分页边界测试会打在一个**真正分页**的
  接口（用户列表）上，而不是这里。**代价（若判断有误）**：部门数量极大时该接口会一次返回全量。

- **P1-A-9：同名校验是**同级**范围内的，且由 service 层在事务内完成。**
  两个不同父节点下可以各有一个「研发部」（现实中的组织就是这么命名的）；不建数据库唯一索引是因为
  逻辑删除后必须允许重建同名。这正是 P0 评审留下的「承诺了但不存在」的那条校验，本任务开始逐模块补上。
  **代价（若判断有误）**：并发创建同名同级部门时仍可能双双成功（无唯一索引兜底）—— 见下方遗留。

- **P1-A-10：删除守卫返回 400 且带**可区分**的文案。**
  「存在下级部门」与「部门下存在用户」是两种不同的用户动作，都返回同一句泛化错误会让人无从下手。
  **代价（若判断有误）**：错误文案成为事实上的契约，前端若要按文案分支就会很脆 —— 所以前端应依据
  状态码 + 是否展示 msg，而不是匹配文案。

- **P1-A-11：补齐了种子里缺失的按钮权限码（`system:dept:*`、`system:post:*`、`system:role:query`）。**
  原本种子里只有用户/角色/菜单有按钮码，部门与岗位只有列表码。不补的话，**任何非管理员角色都不可能
  被授予部门/岗位的新增、修改、删除** —— 权限模型会是残缺的，而且这种残缺不会报错，只会表现为
  「怎么授都授不出这个权限」。已重新播种并查库确认 33 条菜单、11 个新码就位。
  **代价（若判断有误）**：种子数据文件变大；重新播种会刷新这些行（这是既定的种子语义）。

### 实施中发现的自身缺陷（已修）

- 编辑 `seed_data.py` 时一次误操作**去掉了 `system_role` 那行末尾的换行**，把两个元组接到同一行。
  语法仍然合法，所以不会有任何测试或类型检查报错 —— 属于「静默变丑且丢了一条按钮」的那类问题。
  发现方式是紧接着的 `read` 复查。教训：用 `old_string` 做替换时，**不要在同一段字符串里同时改动
  内容和结构**，一次只做一件事。
- 路由 `router.py` 的编辑一开始被文件策略拒绝，导致 19 条测试全部 404。这一步的教训是：
  「代码写完」与「代码被挂载」是两件事，测试红了要先分清是哪一种。

### 已验证

- 后端 `pytest`：**175 项通过**（P0 的 130 项 + 任务 1 的 25 项 + 本任务 20 项）
- `test_dept.py` 覆盖：物化路径（根/子/孙）、**移动后整棵子树路径重写**、自环与挂到自身下级的拒绝、
  有下级或有用户时拒绝删除、软删除落库、同级重名拒绝与隔级同名放行、改名不与自身冲突、
  树形返回、treeselect 形状、按名筛选、404、以及三条权限断言（401 / 403 / 403）
- 重新播种后查库确认新权限码就位（33 条菜单）

## P1-A 任务 3：岗位 CRUD

### 裁定

- **P1-A-12：`create_time` 这类 `server_default` 列必须在 flush 后显式 `refresh`。**
  它的值只存在于数据库里，flush 之后访问它会触发一次惰性 SELECT —— 而这次访问发生在 Pydantic
  解析响应体的时候，那里没有 greenlet，于是抛 `MissingGreenlet`，最终表现为一个 500。
  已在 `create_post` / `update_post` 里补 `await db.refresh(...)`。
  **注意**：部门模块没有暴露这个问题，**仅仅因为 `DeptOut` 里没有 `create_time`** ——
  也就是说这是一个潜伏在所有「输出 schema 包含 server_default 列」的写接口里的坑，
  而不是岗位模块特有的。凡新写一个带 `create_time` 的输出 schema，都要记得这件事。
  **代价（若判断有误）**：每次写操作多一次 SELECT（换取正确性，值得）。

- **P1-A-13：批量删除是**幂等**的。**
  `DELETE /post/{ids}` 里不存在的 ID 被静默跳过，不报错。删除天然幂等，重复提交（网络重试、
  双击）不该得到一个错误。**代价（若判断有误）**：调用方无法从响应里得知哪些 ID 实际被删了。

- **P1-A-14：ID 列表格式不对返回 422 而不是 500。**
  `/post/1,abc` 是调用方的输入问题，不是服务端意外；500 会误导排查方向。已在路由层用一个
  小函数做格式校验。**代价（若判断有误）**：多一处手工校验（本可以用 Pydantic 的路径参数类型做，
  但逗号分隔的列表用那种方式表达会更绕）。

- **P1-A-15：`optionselect` 只返回**启用**的岗位。**
  否则「已停用」的岗位仍然能被新用户选中，停用就失去意义。**代价（若判断有误）**：
  需要为「给历史用户保留旧岗位」的场景另开接口（目前不需要）。

- **P1-A-16：岗位列表是第一个**真正分页**的接口，P0 评审遗留的分页缺口在此闭合。**
  P0 评审指出 Review Focus #4「分页边界不会 500」只在模型层被证明过。本任务在**接口层**补了
  6 条边界断言（超大 `page_size`、`page_size=0`、负 `page_num`、非数字的 `page_num`/`page_size`
  → 422、以及真实切片 `page_num=2&page_size=2` 只返回 1 行而 `total=3`）。
  **代价（若判断有误）**：无；这条缺口本来就必须补。

### 实施中发现的自身缺陷（已修）

- `PostOption` 最初继承 `BaseModel` 而不是 `ORMModel`，于是无法从 ORM 对象校验，报
  `model_type`。是**测试**把它抓出来的（`test_optionselect_shape`），不是类型检查 ——
  Pydantic 的 `from_attributes` 配置错误在静态检查里看不出来。

### 已验证

- 后端 `pytest`：**199 项通过**（P0 的 130 + 任务 1 的 25 + 任务 2 的 20 + 本任务 24）
- `test_post.py` 覆盖：增删改查、业务键唯一性（含**软删后可用同码重建**这条反向边界）、
  分页信封与真实切片、6 条分页边界、按名/按码筛选、`optionselect` 只给启用岗位与字段形状、
  批量删除与畸形 ID 列表、以及 401/403/403 三条权限断言

## P1-A 任务 4：菜单 CRUD

### 裁定

- **P1-A-17：按节点类型分别校验，而不是一套通用校验。**
  三种节点（目录 M / 菜单 C / 按钮 F）必填与禁填的东西完全不同：按钮**必须**有 `perms`（没有权限码的
  按钮对权限系统是不可见的）、菜单**必须**有格式合法的 `component`、目录**必须没有** `component`
  （目录只渲染子菜单，组件永远不会被挂载）。用一个宽松的通用校验会让这三类错误全部变成运行时才
  暴露的问题。**代价（若判断有误）**：前端新增节点时必须先选类型再填表单（这本来也是它的交互）。

- **P1-A-18：`route_name` 全局唯一，但**空值不参与**判断。**
  它会成为 vue-router 的路由名，重名会静默覆盖另一个页面（这是最难排查的一类前端故障）。
  而按钮节点没有路由、存在大量空值，所以「唯一」不能把空字符串当成一个值。
  **代价（若判断有误）**：不支持两个不同分支下刻意同名的路由 —— 这不是合法需求。

- **P1-A-19：删除菜单时**显式**清理 `sys_role_menu`，不依赖外键的 ON DELETE CASCADE。**
  DDL 里确实有级联，但如果只靠它，「删菜单会收回权限」这件事就只存在于迁移文件里，读 service 代码的
  人看不到。写明这一行换来的是可读性。**代价（若判断有误）**：多一次 DELETE（幂等且廉价）。

- **P1-A-20：`/list`、`/treeselect`、`/roleMenuTreeselect/{role_id}` 必须声明在 `/{menu_id}` 之前。**
  这是 FastAPI 的匹配顺序决定的，已写进模块 docstring —— 顺序错了的表现是诡异的 422，而不是报错。

### 实施中发现的自身缺陷（已修）

- 测试里我把枚举成员写成了 `MenuTypeEnum.DIRECTORY`，真实成员是 `DIR`。**RED 阶段就抓到了**
  （`AttributeError`），没有浪费实现时间 —— 这正是先跑失败测试的价值。
- 修它时我的 `replace_all` 只覆盖了 `menu_type=...` 这一种写法，漏掉了 dict 字面量里的
  `"menu_type": ...` 与断言里的 `== ...` 两种形式，于是多跑了两轮。
  **教训**：批量替换要按**语法上下文**清点全部形式，而不是看到一个就以为只有这一个。

### 已验证

- 后端 `pytest`：**216 项通过**（P0 的 130 + 任务 1 的 25 + 任务 2 的 20 + 任务 3 的 24 + 本任务 17）
- `test_menu_crud.py` 覆盖：三类节点的必填/禁填校验、`route_name` 重名拒绝与多空值放行、
  改名不与自身冲突、有子菜单时拒绝删除、**物理删除**、删除时角色关联被清理、
  树形列表、treeselect 形状、`roleMenuTreeselect` 返回 `menus` + `checkedKeys`、404、401、403

## P1-A 任务 5：角色 CRUD、菜单授权、数据范围

### 裁定

- **P1-A-21：`admin` 角色三重保护：不能删除、不能停用、`role_key` 不能改。**
  三者任一发生，就再也没人能进后台（改 key 还会同时让通配权限失效）。这类「自锁」是后台系统里
  最难恢复的故障 —— 数据库里没有别的入口能救回来。停用走 `changeStatus` 时也要拦，
  否则可以绕过 `update` 把自己关在门外。**代价（若判断有误）**：真的需要换超管时得改数据库
  （这本来就该是一次刻意的运维动作）。

- **P1-A-22：切换数据范围时**无条件**先清空 `sys_role_dept`，再按需写入。**
  只在不等于 CUSTOM 时清理是不够的：从「自定义 A,B」改成「本部门」再改回「自定义」时，
  如果中间没清，旧的 A,B 会静静地回来，范围比使用者以为的更宽 —— 而宽出去的可见性是**不会报错**的。
  **代价（若判断有误）**：多一次 DELETE。

- **P1-A-23：`dept_ids` 必须校验存在性，返回 400。**
  这是本轮修测试时暴露的真实缺口：`sys_role_dept.dept_id` 是外键，不校验的话调用方拿到的是
  数据库抛出的 500（且信息量与排查价值都很低）。现在会明确指出哪个部门 id 不存在。
  **代价（若判断有误）**：多一次 IN 查询。

- **P1-A-24：批量授权（`selectAll`）幂等。**
  已经拥有该角色的用户不会被重复插入 —— 否则复合主键会直接报错，而「重复提交」在真实网络里
  是常态。**代价（若判断有误）**：调用方无法从响应里得知哪些是新授予的（与岗位批量删除取舍一致）。

### 实施中发现的自身缺陷（已修）

- 三处数据范围测试用了**不存在的部门 id（11/12）**，触发外键失败。这是测试的错，但它**暴露出
  服务端缺一条校验**（见 P1-A-23）—— 测试写错反而找到了产品的洞，值得记一笔。
- 两处测试引用了 `staff` 用户却没在函数签名里请求创建它的 fixture。**fixture 是按需创建的**，
  同一文件里另一个测试能拿到不代表这个测试能拿到。教训：测试里跨函数「引用」某个夹具造出来的
  数据，等于隐式依赖，必须写进签名。
